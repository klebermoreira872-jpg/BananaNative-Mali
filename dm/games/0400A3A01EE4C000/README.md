# Pokémon Pokopia (`0400A3A01EE4C000`)

A Switch 2 game: update v655360 (the title screen says Ver. 2.0.1), SDK 20.5.25 built for the Switch 2 (`Ounce`). Koei Tecmo's KTGL engine on NVN2, modules `main`, `subsdk0` (WebM movies) and `sdk`. **Plays on the Mac**: the opening, the character choice and the first area's tutorial at about 60 fps, including 31 minutes of the user's playtest with no GPU error and no crash. A save from an earlier run loads and continues. No IPA has been built.

## Rendering

- Frames take about 16.7 ms. A cold file cache, as after a reboot, keeps the game on the loading icon for over a minute, and a clean run there says nothing: check that `[nvn] frame N: … calls` reached about 3,500.
- The lit HDR target is RG11B10, exposure a 2x1 RGBA32F image, tone map `075fd7285c64b798` with a 32³ LUT, final `ed5f4c6386ca621d`, the luminance histogram compute `2118ab534fac88c6`.
- `texraw` pads rows: an RG11B10 dump has a 16-byte stride with 4-byte pixels at the head of each row. It returns one slice of a 3D texture, and serials shift between runs.

## Render size

KTGL's dynamic resolution, found by disassembly of update v655360's main (2026-11-05):

- **The table:** 34 sizes at `main+0x2849658` (u32 widths, then the heights at `+0x28496e0`), read by the getters at `main+0x1129990` / `+0x11299d0`. Level 0 is 960x540 and each level adds 32x18 up to level 30, 1920x1080; levels 31-33 are 2560x1440, 3840x2160 and 7680x4320. The leaf functions at `main+0x1129980` / `+0x11299c0` return 1920 / 1080, but only as a fallback when the display object at `[main+0x35618d0]` is missing; the window size is that object's `+0x48` / `+0x4c`. So `window_fn` has nothing to write here.
- **The controller:** set up at `main+0x22ca40`, which takes the levels from a two-byte config (the maximum to `+0x29`, so `+0x18` / `+0x1c` hold the maximum size); stepped at `main+0x22cd20`, which moves an index down a level list when its late-frame counter passes 1.25 and up when the other one does. The render size is the level's size times a scale, capped at the maximum size; the per-frame budget is 1/60 s.
- **The lists** (`main+0x22d338`), by `oe::GetCurrentGraphicsScale`, `oe::GetOperationMode` and a flag at `+0x8a`: docked at scale 1 (what the host reports docked) `main+0x2804ff0`, levels 24 down to 17 (1728x972 to 1472x828); docked at scale 0 `+0x28055c0`, 30 down to 23; handheld at scale 0 `+0x2808b69`, 20 down to 11 (`+0x2808b60` with the flag); the others are for scale 1 handheld (`+0x2808b73`, `+0x2805160`) and scale 2 (`+0x2808b7c`, `+0x2805198`, `+0x2805458`), 22 down to 1. No list starts at 720p, so `graphics_scale` rows cannot give it.
- **`res_levels`** (`loader.c` `levels_apply`): with `DM_WINDOW_SIZE=<w>x<h>` the host rewrites each list whose first level is larger than the size to start at the largest level that fits and step down from there; the log says `resolution: at most 1280x720 (level 10 of the game's 34, DM_WINDOW_SIZE=1280x720): 9 of 9 level lists lowered`. Phone 1080p and Original lower nothing. The in-game panel's Resolution row saves the same setting for the next start (2026-11-10): the lists are rewritten at load. Seen, not followed (open): the list selector begins by testing and clearing a byte at the pointer in `main+0x3484cc8` before it queries the scale, so it may run again on a scale or mode change; a live cap would also need the original lists kept and the read-only data written while the game runs.
- **On a phone** (a user's Samsung S25 Ultra, Adreno 830, 12 GB, a Turnip driver; Banana Native at `5666bf0c`, before v0.1.3; 2026-11-05): at the game's own lists, docked, the GPU took 36 ms a frame (23 fps). `DM_OPMODE=0` (handheld, starting at 1600x900) gave 35 ms, and `gpu_timestamps segment` did not lower it either. The lists lowered to start at level 10 (1280x720) gave 28 ms (31 fps) with a clean picture. The scene follows the level; the rest of the frame does not (nine render targets are created at a constant 1920x1080, `main+0x10f43ec` and others), and one compute pass, the luminance histogram `2118ab534fac88c6`, took 13.6 ms of a 15 ms frame in light areas whatever the size (open; measured before the Turnip shuffle module of v0.1.3).
- **What breaks:** lowering the table itself (every level above 720p reading 1280x720, so the maximum too) gave 12.8 ms (59 fps), but the ground and objects drew wrongly, also with the 1920 / 1080 getters and the nine constant render target sizes set to 1280x720 as well. Something else assumes the game's own maximum, not found (open): a frame capture would show which pass.

## Link Play on Android

Experimental phone-to-PC local wireless over IP ([issue #177](https://git.eden-emu.dev/moceure/BananaNative/issues/177)). This needs a host build with the optional co-op module and a compatible PC host. It does not provide Nintendo online services. The host mechanism is described once under [Opt-in LDN sessions and virtual UDP sockets](../../../docs/reference/services.md#opt-in-ldn-sessions-and-virtual-udp-sockets).

### Joining a PC host

On Recompia, use the native protocol (`[net] protocol = native`). For this Android adapter, set `[pkp] link_interact_everywhere = false` and `link_story_coop = false`, with no active gameplay Modtopia mods, then restart the PC game. Android advertises the vanilla mods fingerprint `0`; the [pinned PC adapter](https://github.com/Dittobyte/Recompia/blob/75dae2f2ccdada74e6b8ba12ea7de30560a84221/runtime/src/services/ldn_native.cpp) includes Interact everywhere, Story co-op and active gameplay mods in its fingerprint. Story co-op also enables Interact everywhere. These settings are read when the feature installs, so changing the ini while the PC game runs leaves its current session unchanged. A mismatch can hide the host from discovery or refuse a join; check these settings if the host cannot be found.

In the Android launcher, open the game's card menu, then **Game settings > Game > Link Play**. The profile's `link_play 1` enables this row; profiles without it have no row. Settings apply when the game next starts, so leave a running game before changing a connection.

| Choice | Settings sent to the host at the next start |
|---|---|
| Off (default) | `DM_COOP=off`, `DM_COOP_INTERNET=0`, empty `DM_COOP_ROOM` |
| Join PC host, on the same LAN | `DM_COOP=join:<host IPv4>:<port>`, `DM_COOP_INTERNET=0`, empty `DM_COOP_ROOM` |
| Join PC host, Internet / Tailscale enabled | `DM_COOP=join:<reachable host IPv4>:<port>`, `DM_COOP_INTERNET=1`, `DM_COOP_ROOM=<host room code>` |

The address accepts IPv4 with an optional port; the default is 47600. The special literal `localhost` is accepted for a same-device test; other hostnames and IPv6 are not accepted by this protocol. Use the PC address reachable from the phone. A public or Tailscale address needs Internet mode and the host's 16-symbol room code; the dialog accepts the code's spaces and hyphens. An invalid address or code leaves the dialog open without saving a partial connection. Off retains the saved address and code for a later visit.

These choices override global `env.txt` values for this supported profile, including stale co-op values when Off or an invalid saved connection is selected. Explicit per-game environment lines and the test app's `env-<title ID>.txt` are applied afterwards and can override the choice. Check those overrides if the game's behavior differs from the row. Profiles without `link_play 1` receive no Link Play environment overrides.

Use distinct host and visitor save identities, with Link Play already unlocked in both saves: a copied identity may be rejected, and an early tutorial save cannot use the terminal yet. Keep existing saves intact. Internet mode proves the room code and tags messages but does not encrypt the game traffic, so anyone on the network path can read it. The room code authenticates the session; this module does not encrypt its game traffic. Tailscale is an optional way to reach the host, not a discovery mode. The dependency's diagnostics can contain peer addresses, room codes and node IDs, so remove these before sharing logs.

### Optional module and provenance

The host integration is inert until `DM_COOP` is enabled. It builds offline when the portable module is absent. ## Online events (opt-in)

Some events (Apples to Applin, 2026-11-16 to 2026-12-01) need an internet connection the first time they are played and stay hidden on a console that has none. Game settings › Game options › **Online events** (`DM_ONLINE=1`, off by default, experimental) tells the game it is online: `nifm` reports the network available with a private address, the network clock task succeeds and the network clock reads the user clock (so Time of day moves both). Nothing is sent: every socket call still fails and the delivery cache stays empty, as in Recompia's `[pkp] online_events` (`runtime/docs/CONFIG.md`, Recompia v0.14.0, GPL-3.0). The proxy query then answers no proxy and `nsd::Resolve` / `ResolveEx` keep the name. Hooks: `hle_net.c` (`nifm`, `nsd`), `hle_sdk16.c` (the network clock task), `hle_time.c` (the network clock). Current: not run on a phone (unverified): whether the game's event list then shows the event, and whether it shows connection errors for services that cannot answer (Recompia's note; turn the option off then). **Trace (open):** the game still showed OFFLINE with the first version of this option. Its own code (update 655360, `main.elf`): a network monitor (main+0x163b540) polls `nifm::IsNetworkAvailable` every 3 s and wakes waiters on a change to available; a request task (main+0x1acd2ac) runs Submit, the on-hold query, then `IsNetworkAvailable`; the HTTP layer (libcurl, main+0x1566948, +0x1769210, `nsd::ResolveEx` at main+0x176908c) asks the proxy and the name service per request. The code does not show which result the OFFLINE label and the event list read, so it is not proven that this option flips them. Run with `DM_ONLINE=1 DM_NET_TRACE=1` and read the `[net]` lines: the order of the calls, and the last call before the game gives up (probably a `socket::GetAddrInfo` / `Connect` to a Nintendo server, which cannot succeed here), says whether the label needs a server answer. Events that follow a calendar date also need Time of day set into their window.

## Mods and hosting a world (opt-in, not run on a phone)

- **Mods** (Game settings › Game options › Mods, profile key `mods`): the player imports a .zip of replacement files (`Mods.importZip`: an outer folder named like the zip, a version number or `romfs` is dropped; paths that leave the folder are refused). ## Screen shape: the world and the UI at the device's shape

Game settings › Aspect ratio › **Screen shape** (game.tsv `aspect screen`; the launcher passes the window's shape as `DM_VK_PICTURE_ASPECT`, 1:1 up to 16:9, a wider window keeps 16:9) shows the game's 16:9 frame at the screen's own shape, and [`pkp_aspect.c`](../../host/android/pkp_aspect.c) makes the game draw for it, k = shape / (16/9) (0.75 at 4:3):

- **World cameras:** the scene camera gets the taller view of the Fold 7 work below; every other 16:9 perspective camera gets the same projection (P11 x k, horizontal reach kept).
- **UI:** a 1920x1080 plane 1303.6 in front of 45-degree perspective cameras (near 0.1, far 20000) and orthographic 2D cameras (P00 = 2/1920): their P11 x k lays the layout out 1920 wide and 1080 / k high, squeezed into the frame, so the stretched picture shows it in its proportions. Text comes in screen pixels: the 2D batch constants (`(2/w, -2/h, -1, 1)`, main+0x17b97b4) of text programs 0x1a, 0x11, 0x14 get the same squeeze (gate main+0x17b9804); the scene's own composite (another program, same target) is left alone.
- **ScreenLayout panes** (transform update main+0x1f71de0, gate at its tail main+0x1f72270: global matrix final, children next). The layouts anchor everything at the centre (+0x10d is always 0x11), so the host places the edges: a pane under a centred full-screen container at least 300 from the centre moves 540 (1/k - 1) toward that edge, its group with it (field HUD key help and tool wheel, Pokedex header and filters, camera-mode controls, the title's copyright). The same holds under a large centred panel (>= 1200x900, scale within 10 %: the bag's and menus' frames), for the key help layout's full-width bar straight under its root (1920x72 at -463: bag, menus, Pokedex), and by a full-width band's near edge (within 160 of the 16:9 frame's edge: the bag's item window; side panels such as the menu's map stay beside their panel, as at 16:9). A centred pane that covers 16:9 but not the taller screen is enlarged by 1/k on both axes (loading screens, fades, the Pokedex background): leaves through their matrix (pictures draw from their texture size), containers through their size.

Checked on a Retroid Pocket Nova (1280x960, Turnip) at 4:3, and at 16:10 and 1:1 through `DM_VK_PICTURE_ASPECT`: title, field, menu, bag, Pokedex, camera mode, a dialogue with choices, loading screens and fades. Known: the title screen keeps black bars above and below (not a camera, scissor or mask: unexplained); the Pokedex bottom bar ends about 20 px short of the edge. Switches: `DM_PKP_UI=0` (world only), `DM_PKP_EDGE`, `DM_PKP_EDGE_GAP`, `DM_PKP_EDGE2`, `DM_PKP_COVER`, `DM_PKP_TEXT_PROGS`, `DM_PKP_CROP` ([env switches](../../../docs/env_switches.tsv)).

## Experimental Fold 7 scene-camera aspect (opt-in)

For Pokopia v2.0.1 / update 655360, exact **main build ID** `76a489f3bd3642fa5e18bd83d32c98ba`, Android has three build-pinned observation gates for scene-camera submission, the perspective builder and the completed projection. Set `DM_PKP_ASPECT=1.109756` before starting the game for a 2184 x 1968 Fold 7 inner-screen picture. Use matching picture presentation, for example `DM_VK_PICTURE_ASPECT=2184:1968`; the existing Stretch presentation also fills that screen. Unset or set `DM_PKP_ASPECT=0` for the original 16:9 camera. **Restart the game after changing this setting.** Invalid, non-finite, out-of-range and 16:9-or-wider values leave the camera unchanged.

The correction increases vertical FOV while retaining the original horizontal reach. The aspect field remains 16:9 because changing it caused terrain/LOD cells to disappear. Each of the eight registered scene cameras retains its latest corrected FOV, so another camera's zoom changes cannot cause it to be corrected twice. A 32-value recent history also recognizes the game's copied render cameras after their source changes FOV. This covers the observed render-camera path; arbitrary orphaned copies retained across more than 32 later corrections have not been established. The gates execute their original instructions, and only this exact main build receives them. Unlike the fixed `VARIANT_CUTS` used by Fire Emblem, these callbacks adapt the game's changing FOV and its copied cameras to a runtime-selected display ratio; all addresses remain in this profile's `patches.py`.

**Scope (at the time):** world camera only; the UI is now laid out for the shape too (Screen shape, above).

**Focused checks (2026-11-12):** Against Android base `29fb81de35f0013cfe0e2efabd878b64b59582f0`, the NDK callback harness ran on a Fold 7 and passed all 14 opt-in, build, projection and startup cases. Reproductions failed before the malformed-value, scene-history eviction and changed-source/copy fixes, then passed after them. These callback checks use synthetic camera structures and do not replace the gameplay/driver comparison below.

**Current gameplay evidence (2026-11-12):** On Android base `29fb81de`, a same-APK OFF/ON comparison used the same populated Ver. 2.0.1 world, Fold 7 (Android 16, Adreno 830), 2184 x 1968 display and Turnip Mesa 26.2.3 (`fbc44a3bcc`, Vulkan driver ID 18). The corrected world matched the 16:9 reference proportions, retained horizontal coverage and added vertical coverage; terrain rendered coherently and camera input worked. The FOV changed from 42.0 to 63.2 degrees at `DM_PKP_ASPECT=1.109756`. After rebasing to `0bac816c`, a clean APK rebuild preserved all five packaged native libraries and the game overlay byte for byte; the installed APK SHA-256 was `49847D9B4F2F54106D3236092E4D2430EA653DE96C44ED6A89EB29608FD2B40F`. That rebuilt APK also ran the corrected Turnip world for over 39 seconds and responded to camera input. Performance parity was not measured.

**Qualcomm limit:** The Qualcomm comparison used the same `29fb81de` comparison APK for OFF and ON, with the stock Qualcomm driver (driver ID 8, `0x80320027`, Vulkan 1.3.284) and `DM_VK_PREWARM=0` in both runs. Terrain was already incomplete with correction OFF. ON briefly showed corrected proportions and the same terrain defects, then Android reported `LOW_MEMORY` before sustained gameplay or input acceptance. Stable Qualcomm gameplay is not verified; the additional coverage's memory cost has not been excluded. These outcomes do not establish a camera-only rendering regression.

**Earlier evidence:** Local v0.3.0 phone tests also showed improved world proportions with Turnip and incomplete terrain with the stock Qualcomm driver. Those historical observations are distinct from the current-source checks above.
