# Nintendo Switch 2 Welcome Tour (`040057C02159A000`)

A Switch 2 game: update v262144 over the base game, SDK 20.5.29 built for the Switch 2 (`Ounce`), NVN2. NintendoWare's Bezel Engine, modules `main`, `subsdk0`, `subsdk1` (movie), `subsdk3` and `sdk`.

**Status on Android:** in bring-up. The profile, its shader tables and three host answers come from upstream nxnative's pull request [#1425](https://github.com/seedds/nxnative/pull/1425) (open on 2026-11-16), where the game plays on the Mac (M1 Pro, macOS 27.2): past its intro video to the tour, its menus and exhibits, at about 60 fps. It has been packed and its Android shader library built here (below). On the phone (AYN Thor, 12 GB) it plays its intro video, then runs out of memory 11 s in; with RAM saver on it loads (current, below).

## What it needs

| Setting | Where | Why |
|---|---|---|
| `mem_alias 0x400000000`, `mem_reserve 0x550000000`, `mem_stack 0x10000000`, `app_pool 0x240000000` | [`game.tsv`](game.tsv) | the Switch 2's 9 GB, as Splatoon Raiders and Star Fox: with `profile_guess.py`'s 5 GB block (a 4.4 GB alias region and a 1 GB pool) Bezel's allocator found no room at boot on the Mac ([Bezel Engine's two memory setups](../../../docs/reference/memory.md#bezel-engines-two-memory-setups)) |
| `sys_resource 0x1000000` | `game.tsv` | the NPDM declares 16 MB, so virtual address memory is on |
| `modules` without `subsdk2`, `subsdk4` | `game.tsv` | C / libc modules main takes nothing from that the host does not supply |

There is no game-specific patch, and only v262144's build row: the base game alone has not been run.

## Files

- A NUP v2 set: `Nintendo Switch 2 Welcome Tour.nup` (the base) and `Nintendo Switch 2 Welcome Tour.update.262144.nup`. The display version `v262144` is a placeholder: no control data gave a better one.
- RomFS: 722 files, 1.49 GB, most of it Bezel Engine archives (`Archive/*.bea`).

## Shaders

6,766 in [`shader_map.tsv`](shader_map.tsv), from upstream (BNSH / BAHS in the RomFS and `main`; 7 mesh shaders and a task shader of `forward_plus.bfsha` are read by `main`'s mesh reader). On upstream's chain `3df44a5a4e0c` (2026-11-09), 29 failed to translate: 28 on Ampere instruction `0x3ad`, which is not implemented, and one `AST` with an offset register and an address; in 9 more the translator deleted 429 bindless accesses (their results read 0). 6,102 pipeline pairs prebuild.

The Android library (2026-11-16, Windows, vk chain `59e8d600c339`, from the NUP v2 set): the split finds all 6,766; the 12 variations of `gfxshaderrt/*.bnsh` in program slot 6 (ray tracing, stage byte 8) are left out (`shader_split.py` leaves such a shader out alone; before, it dropped the whole archive: the shaders.md entry "A ray tracing shader in NVN2 BNSH program slot 6 drops its whole archive", from the shader fixes pull request). 6,753 translate, into a 45.7 MB `dmsh_vk.lib` (7,515 modules, all valid for spirv-val vulkan1.3); 3.5 minutes with `J=12`. Not translated (current, open): the 7 mesh and the task program of `forward_plus.bfsha` (`mesh program without a mesh layout`: no `mesh` job for them), one hull shader (`AST` with an offset register and an address), and 4 pixel shaders whose reflection has more bindings in one stage than the range. The split also logs that 5 mesh programs' per-primitive values are not their pixel shaders' flat inputs `[36, 40]` (not looked into).

## Controllers

The exhibits use the Joy-Con 2's features: the mouse sensor, the Joy-Con 2 npad styles and HD rumble. Upstream drives them with its Switch 2 controller transport on the Mac (issue [#1267](https://github.com/seedds/nxnative/issues/1267)); on Android the host still answers that no controller has a mouse sensor ([The Joy-Con mouse pointer](../../../docs/reference/services.md#the-joy-con-mouse-pointer)), so the game should run, but its cursor will not move and the mouse exhibits cannot be played (open).

## Open

- First phone run (2026-11-16, system driver): the 9 GB layout mapped and the graphics system came up; it crashed in `hid::GetJcmsState` as it set its controller styles (resolved, below).
- Second phone run (2026-11-16, AYN Thor, Turnip T30): it aborted 3.5 s after boot in `hid::GetMousePointerSpeedScale` (Result 0xe15; resolved with upstream's other hid hooks, below). `main` also builds `movie::Decoder` through its base-object constructors (upstream's fix for Mario Tennis Aces, ported).
- The whole-phone freezes (two runs, 2026-11-16; resolved): a 4 GiB + 4 KiB ray tracing heap sized from an output the host never wrote, placed whole as driver memory as the intro video began ([Acceleration structure sizes left unwritten](../../../docs/reference/nvn-objects.md#acceleration-structure-sizes-left-unwritten-nvn2-ray-tracing)). With the fix: no freeze, 700 MiB of pools placed, the intro video and 288 frames at about 25 fps (recording 41 ms a frame at p50, most of it texture preparation).
- Memory on a 12 GB phone (current, open): the game maps about 6 GB of its pool by its first seconds (asset loading: about 640 texture-sized pools in 0.2 s), and 11 s in, at 5.0 GB resident, Android's low-memory killer ended it (available memory 2.8 GB). With Game settings › RAM saver on (`DM_MEM_FILEBACK_KINDS=shader,texture`) a player's run on the same phone (2026-11-16, Turnip T30) played 2.5 minutes, 5,400 frames, until the player closed it: 41–46 fps once in the tour (GPU 14 ms, recording 18.8 ms a frame, 2,250 draws, 83 render passes), footprint 4.5–4.9 GB, GPU memory up to 2.0 GB. RAM saver backed only 143 MiB of pools with its file (186 MB written, 3 MB read back) and the footprint was about the killed run's, so whether it is why the run lived is open (the memory the rest of the phone held differs from run to run). Textures came late at first: that run was the first on the device, with no pipeline cache, and made 485 pipelines in 21 s, most of them in the background, whose draws are skipped until they are ready; the next runs start with its 261-pipeline cache (not measured yet). Also seen: 7.08 million write-protection faults in 2.5 minutes for the 420 textures the CPU writes (656 re-uploads), and long frames of 0.45–0.9 s with major page faults. Not tried yet: the profile's low-RAM keys (`low_ram_app_pool_mb`, `low_ram_place_part_mb`) and a 16 GB device.
- Ray tracing (upstream, on the Mac): `nvnQueueBuilderSetRayTracingMemorySize`, `nvnProgramBuilderSetRayTracingModules`, `nvnProgramBuilderSetProgramRayTracingFlags`, `nvnProgramBuilderSetMaxTraceRecursionDepth`, `nvnProgramBuilderSetMaxCallableRecursionDepth`, and `nvnProgramGetShaderGroupHandle` are unimplemented (`[RED]`, once each at boot), as is `nvnDeviceRegisterFastClearStencil`. What the game draws with them is not known.
- Phone, the player's run above: `[RED] vk: NVN format 0xba27ba00 has no Vulkan format` and `… format 0x50001 …` once each at about 52 s (not NVN formats: a registered texture holding other data). Open. Formats reach the replay only from the game's builder (`nvnTextureBuilderSetFormat`, or a builder it never set to defaults), so `nvnTextureInitialize` now logs a texture whose format is no NVN format, with its target, size, flags, pool and the game's call stack (`[RED] [nvn] TextureInitialize: format … is no NVN format`); registrations log a texture object without the live `'TEX'` magic. A warm-cache run of 80 s (2026-11-16 20:47, past the NPC's first frames) logged neither and no bad format: the formats came in the player's first, cold-cache run, where the NPC's pipelines were still being made in the background. Two cold-cache runs since were killed by the low-memory killer at about 12 s (the background pipeline compiles add to the footprint), so the cause is not found yet.
- `[RED] vk: shader 1802f08a775d438a binding 260: texture ID … has no view of shape 0x3` for 8 IDs at the same time (resolved: not a fault). The shader is `npc01_boy.bnbshpk` variation 6's pixel shader, binding 260 a cube texture, and its handle comes from data that holds floats there: ID 629146 is 0x9999a, the low 20 bits of 0.3f (0x3e99999a). The material leaves its cube slot unset and its branch does not sample it; the replay binds the null view (zeros), as for Donkey Kong Bananza's 2D textures in volume slots. Only the first 8 are logged.
- The intro video's cost (current): the game's CPU writes each 3840x2160 video frame into a write-protected RGBA texture, so the texture uploads again each frame (237–300 re-uploads in 300 frames, about 24 ms of texture preparation a frame: the intro runs at about 25 fps). The log's "write-protection faults" counts pages released (a fault releases up to 1 MiB on each side), about 8,700 a frame there, 7.06 million in the first 900 frames, none after the video.
- RAM saver's size threshold (current): the game's texture pools are small (1.4–11 MB each, 1.77 GB in all), below `DM_MEM_FILEBACK_MB` (64), so RAM saver backed only 143 MiB of them. With `DM_MEM_FILEBACK_MB=1` it backs 2.98 GB, and a warm-cache run with it lived 80 s (MemAvailable steady at 5.1 GB) after `am kill-all` had dropped the cached background apps; one without that was killed at 8 s (4.1 GB resident instead of 5.0: pages the game just wrote stay dirty until written back). The game's touched guest memory grows to about 4 GB while it loads (`/proc/<pid>/smaps`: guest block 1.3 → 3.9 GB in 9 s; host malloc 460 MB, driver maps 774 MB); the host does not touch mapped pages itself (`alias_initialize` clears only pages mapped before).
- When the low-memory killer kills the launcher's main process (adjustment 900) during a run, the game logs `window 0x0 (none: presents are dropped)`: it loses its window (open; seen twice on 2026-11-16, each time a few seconds before the game process itself was killed).
- RAM saver is not enough on its own: a run with it (2026-11-16, 20:35) was killed by the low-memory killer 10 s in at 4.9 GB resident, while the player's run lived; a smaller reported total (`DM_APP_POOL_MB=6144`) made the game map more (6.75 GB, killed at 5.2 GB resident), so it does not size its memory from that total.
- Upstream also logged `[RED] nn::codec H.264: a packet refused with 12 pictures waiting for a released buffer` a few times in the videos, and `[RED] stage 0 cb7 has no uniform buffer bound` once.
