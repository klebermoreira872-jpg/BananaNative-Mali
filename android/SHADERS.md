# Shaders on Android: SPIR-V for Vulkan

The Android port runs the game's shaders as SPIR-V on Vulkan 1.3 (first device: Adreno 840, [PORTING.md](PORTING.md)). They are translated offline, as on Apple platforms: the same translator makes the SPIR-V, and the Metal half of the chain (SPIRV-Cross, the MSL rewrites, the Metal compiler) is left out. This page has the build, what was kept of the Apple chain, the descriptor ABI the Vulkan replay (`dm/gfx/vk_android`) binds against, the library format, the results on Donkey Kong Bananza and the open problems.

## Status (2026-11-02)

- **Works:** `DM_GAME=<id> python3 dm/gfx/tools/vk_android_build.py --target vulkan <package dir> <output cache dir>` translates a game's shaders to SPIR-V and writes one library (`v-<DMSH_VK_CHAIN>/dmsh_vk.lib`, zstd modules) with the descriptor ABI of `dm/gfx/nvn/dmsh_abi_vk.h`. `--check <lib>` reads it back as the replay would and runs spirv-val on every module.
- **Validated:** Donkey Kong Bananza (040074A01BF12000, update 458752), library `v-9b3a2294056a` (chain `725d300e1fae`, inputs `5dd843bed8d1`): 22,852 of 22,852 shaders translated with the Android answers, 24,034 modules (22,852 base, 1,149 `MOD_UINT`, 33 `MOD_UINT_MIXED`), every one valid for `spirv-val --target-env vulkan1.3` at build time and after `--check`. 364.5 MB library (1.82 GB of SPIR-V). No NVIDIA capability or extension left. The Apple translations are byte-identical with the answers unset ([Translator answers](#translator-answers)); `DMSH_CHAIN` moved to `725d300e1fae` because `Program.cs` changed. Nothing has gone through Adreno's compiler yet. The replay's own self-test passed on the phone (branch android-vk), before draws.
- **Packed:** `scripts/pack_android.py` puts the library into `<pack>/shaders/v-<DMSH_VK_CHAIN>/` ([README](README.md#pack-a-game)).
- **Replay:** the loader, binder, variants, alpha test, pipelines, draws and dispatches are in `dm/gfx/vk_android` ([What the replay does](#what-the-replay-does)). The graphics selftest draws (with the alpha test) and dispatches through them with its own shaders and passes on the Android emulator; `t_android_shlib` walks all of this library's entries on the Mac and decompresses its variants. No DKB frame drawn yet, and no DKB module through Adreno's compiler.
- **Upstream translator (2026-11-03, branch android-xlate2, library version `0b077f88b2c8`, chain `513b0310a6c9`):** upstream nxnative's Ampere decoder / ALU / memory changes (c8521eeb, 0a759de7, 03d92a9f, 3fe755a2 LDSM stride), the TXQ type fix (d145b956) and the split readers, with this fork's warp-segment fix (8fac22d9) kept. DKB: 22,852 of 22,852 translated before and after, every module valid; 2,322 entries have a different module (ps 2,124, vs 168, cs 30). The ps / vs ones are control flow only (GotoElimination: loop wrappers and duplicated returns gone); the cs ones are agl's 24 upscaler network shaders (`agl_ndsr.pck`, shared memory addresses by their stride, fewer `FAbs`) and 6 others (`agl_technique_pfx`, `agl_common`, `SilverStarPass`). Not byte-identical, so no `vk_android_same.tsv` row: phones rebuild their library. The DKB split with the new `shader_split.py` gives the profile's four tables byte for byte. Mario Kart World 1.8.0 (profile of branch android-mkw2): 11,568 of 11,604 translate (11,524 before; failures 80 → 36: cs 25 → 2, ps 29 → 8, vs 13 and all 13 domain shaders unchanged), 471 common entries with a different module (ps 320, cs 85, vs 66), every module valid. The figures were measured on the intermediate version `f2299a2fa69f`; adding upstream's `DMSH_C0_DISPATCH_NVN2` to `dmsh_abi.h` (NVN2 compute's workgroup counts at c0 + 4, which the replay now fills) moved the chain to `513b0310a6c9` and the version to `0b077f88b2c8` with the same modules (only the 24 header bytes that carry the versions differ). Library SHA-256: DKB `de76d0eee01e4502bf2a8e7aae67a4e74a2c18960cf4042756251fa0ad833c45`, MKW 1.8.0 `69b27201866d1a0b269775a8fa38116335d7258a4938796e7e1d71e53e5e4c53`.
- **Build cache, resumable (2026-11-03, library version still `e38a586a8a89`):** one result file per shader, a killed build resumes, progress lines; the translator and the validator can be shared libraries called through `ctypes` (the phone's form, ONDEVICE.md). A full DKB build with it equals `v-e38a586a8a89` byte for byte, and so does a build resumed after a third of its results were deleted, so the version did not move ([Versions](#versions), `vk_android_same.tsv`).
- **Delta updates (2026-11-04, version `6607c8d19abc`):** after a tools change a phone keeps every shader whose library entry is unchanged (the profile's `vk_delta.tsv`) and translates only the others; the result is the full build byte for byte, and an older library of the same ABI plays meanwhile ([Delta updates](#delta-updates)).
- **Not done:** `SINT`-attachment and transform-feedback variants. Integer vertex formats into float inputs are a rewrite at pipeline time, not a library variant ([Stage interface](#stage-interface)).
- **Next steps:** (1) the graphics selftest on the phone (Adreno's compiler, push descriptors, vertex input dynamic state, null descriptors: the emulator has none of them); (2) a DKB run with `DM_VK_SHLIB_CHECK=1` (every module and compute pipeline through Adreno's compiler); (3) DKB's title frame.

## Build

```sh
DM_GAME=040074A01BF12000 python3 dm/gfx/tools/vk_android_build.py --target vulkan <package dir> <output cache dir> [key...]
python3 dm/gfx/tools/vk_android_build.py --check <output cache dir>/v-<V>/dmsh_vk.lib    # read it back, spirv-val every module
```

- The package dir is the one `dmsh_build.py` takes (`shader_split.py`'s output); the profile's tables give the keys, pairs and answers. Each shader is read from the record the map names once that record's hash is its key; the map's numbering is one split's (a split of the base, update and DLC RomFS together numbers them otherwise), so a record that is not the key's is looked up by key in the package's files of that stage, and a key the package lacks stops the build before any translation ([A shader package of another split](../docs/reference/shaders.md#a-shader-package-of-another-split-gives-shaders-other-shaders-code)).
- Needs: Python 3.14 (`compression.zstd`; or `backports.zstd`), the .NET 10 runtime for the vendored translator, `spirv-val` (SPIRV-Tools: `brew install spirv-tools` or `micromamba install -c conda-forge spirv-tools`). No Xcode.
- Output in `<output cache dir>/v-<DMSH_VK_CHAIN>/`: `dmsh_vk.lib` (the library), `index.json` (the same reflection as JSON, for tools), `inputs.tsv` (the stamp: game and profile inputs, as the Apple libraries carry), `_vk_build.json` (each key's status). `DMSH_VK_LOOSE=1` also writes each module as `spv/<key>.spv`.
- **Results and resuming.** Each shader's result (its modules after zstd, its reflection, the input locations a pixel shader reads) is one file `<results>/<key>.r` (default `v-<V>/results/`, `DMSH_VK_RESULTS` elsewhere), written to `.tmp` and renamed, stamped with the tools digest (below), the profile inputs digest, the codec setting (`DMSH_VK_RAW`) and the key. A run skips every key with a valid result and translates the rest in batches (`DMSH_VK_BATCH`, default 64 shaders a translator call, `J` batches at a time): pixel and other stages first, then the vertex shaders, whose padding reads their pixel shaders' inputs from the result files. The library, `index.json` and `_vk_build.json` are always written from the result files (the reflection goes through JSON once, as `index.json` writes it). Failed shaders are results too (deterministic); a translator that dies (exit code other than 0 / 1) leaves its batch without results, so a rerun redoes it. A killed run leaves at most its unfinished batches (`.tmp` files and `results/.work/`, removed by the next run). The results stay as the build cache of that version (434 MB for DKB); `DMSH_VK_KEEP=0` deletes them once the library is written.
- **Progress:** `progress <done> <total> <stage>` lines on stdout (`translate` after every batch, then `library`, `done`), and the same as JSON in the file `DMSH_VK_PROGRESS` names (replaced by rename). The total is the shader count of the profile's `shader_map.tsv` (or of the keys given), known before any translation; `done` counts the result files, so it survives a restart.
- **Tools in process:** `XLATE` or `SPIRV_VAL` naming a `.so` / `.dylib` loads it with `ctypes` instead of starting a program: the translator's library form (`dm/gfx/tools/dmsh_xlate_android`, `dmsh_xlate_main`; its embedded source digest is checked against the lock, there are no dlls to fingerprint) and SPIRV-Tools' `libSPIRV-Tools-shared` (`spvValidateWithOptions` with spirv-val's default options in the `vulkan1.3` environment; the same first error line as spirv-val). `ctypes` drops the GIL for both, as does `compression.zstd`. On the Mac: `XLATE=<…>/libdmsh_xlate.dylib` (`dotnet publish dmsh_xlate_android.csproj -r osx-arm64 -p:NativeLib=Shared -p:OutputType=Library`) and `SPIRV_VAL=/opt/homebrew/lib/libSPIRV-Tools-shared.dylib`.
- **Worker interpreters (`DMSH_VK_PROCS`, default 1).** The Python half of each shader (`finish`: SPIR-V parsing and rewrites, reflection) holds the GIL, so threads of one interpreter keep it on one core. With `DMSH_VK_PROCS=n` (n > 1) the build makes n sub-interpreters of its own process (`concurrent.interpreters`, Python 3.14; each has its own GIL), since the phone's app may neither fork nor start programs (ONDEVICE.md). Each worker runs the tool's own set-up (profile, tables, answers) and then serves batches with `J / n` threads (at least one): the parent sends each batch with every shader's package record (file, record, offset, length) and, for vertex shaders, their pixel shaders' inputs, which it takes from the result files as before; the workers write the result files, and the parent still writes the library from them. The translator limit (`DMSH_VK_XLATE_J`) holds across the workers (one shared token queue). The library, `index.json` and `_vk_build.json` are byte-identical for any n (checked: DKB and Pokopia subsets, [Versions](#versions)). Only with the library forms of the translator and the validator (a sub-interpreter may not start programs: otherwise one interpreter, with a plain line); workers that cannot start (a Python without sub-interpreters, a module that refuses them) leave the build to threads with a `[RED] shader workers … did not start` line. A worker's error ends the build with its message, as a thread's did. A stop (the app's Pause, `KeyboardInterrupt`) ends every worker after the shader in hand (0.3 s on the Mac; threads finish the batches in hand, 4.3 s); the shaders without a result are translated by the next run. The Android app sets `DMSH_VK_PROCS` to the big and mid cores, at most 4 (`CpuCores.java`). Measured: [Worker interpreters (2026-11-07)](#worker-interpreters-2026-11-07).
- Donkey Kong Bananza on the Mac (2026-11-03): 8 min 16 s with `J=12` from nothing (1,013 s user, 310 s system; it was 10-15 min before the batches); a rerun with every result present writes the library in 8 s. A build killed (SIGKILL) at 3,734 shaders and resumed with `J=6` and the in-process tools (Mac dylibs) translated the other 19,118 in 4 min 48 s and wrote the same library, `index.json` and `_vk_build.json` byte for byte.

### Versions

`DMSH_VK_CHAIN` (`dm/gfx/nvn/dmsh_chain_vk.h`) is the library version: the hash of `DMSH_CHAIN`, `vk_android_build.py`, `vk_android_spv.py`, `vk_android_delta.py` and `dmsh_abi_vk.h` (the tools digest, `vk_android_build.py --digest`), or the earlier version that `dm/gfx/tools/vk_android_same.tsv` names for that digest. After changing any of the files, or after `DMSH_CHAIN` changes, run `vk_android_build.py --header` and commit the header (`dm/tools/tests/test_vk_android_abi.py` fails on a stale one).

A change that cannot change the libraries (a cache, progress, how a tool is called) need not move the version and make every library already on a phone stale: build the full library of a game with the new tools, compare `dmsh_vk.lib` (and `index.json`, `_vk_build.json`) with the current version's byte for byte, and only when they are equal add the row `<new digest>\t<current version>\t<what changed and the evidence>` to `vk_android_same.tsv` (then `--header` leaves the header as it is). A change of output never gets a row. The result files are stamped with the digest, so the build cache starts over either way. The library header records both versions and the ABI; the replay loads a library whose `chain` and `vk_chain` are the ones it was compiled with, or, while that one is missing, an older one of the same ABI ([Delta updates](#delta-updates)). A version that moves sends phones a delta update, not a full build, once its manifest is published.

### Delta updates

A tools change moves `DMSH_VK_CHAIN`, and a phone then needs the library of the new version. Most shaders come out the same (the upstream translator change of 2026-11-03 changed 2,322 of DKB's 22,852), so the phone keeps those and translates only the rest (`dm/gfx/tools/vk_android_delta.py`, used by `vk_android_build.py`):

- **Entry hash.** One shader's library entry as the library stores it: its 64-byte entry with its positions in the file (first module, first binding, c1 offset) zeroed, its binding records, its c1 bytes, and each module's variant, SPIR-V size and SPIR-V words. Not the header (versions), not the codec or the stored bytes, so a zstd of another version gives the same hash. 16 hex digits.
- **Manifest** `dm/games/<id>/vk_delta.tsv` (in the APK's `tools.zip` with the profile): `version`, `game`, `inputs`, then one row per shader key with its entry hash (`-` for a shader that did not build), and `from <older version> <count>` rows: how many shaders a phone with that library translates. Hashes only. Every build writes `vk_delta.tsv` beside its library for the keys it built (from the library read back); a full Mac build of a new version then goes into the profile with `vk_android_build.py --publish-delta <out>/v-<V> [older library dirs…]`, which checks that it is of this tree's version, the profile's game, inputs and keys (the keys the phone builds, `phone_keys`: every key of the map, or for a profile with a [selected set](#selected-shaders) the selection's keys and their paired pixel shaders, so a selected profile's full build is the key-list build of that set), and that every line is one of the fixed hex forms (`manifest_problems`: no path or name can ride along; a home path once leaked through translator binaries). The `from` rows come from the profile's previous manifest and from each older library named. Publishing the manifest is part of every tools change that ships to phones; without one of the APK's version a phone makes a full build, as before.
- **The build.** When the profile's manifest is of this build's version, game and inputs (and no `DMSH_VK_RAW`; a key list too, [Selected shaders](#selected-shaders)): for each shader without a result, an entry of an older library of this game (`DMSH_VK_DELTA_FROM`: files, `v-<V>` folders or folders of them, separated by `os.pathsep`; the app passes the pack's `shaders/`; else the output's cache folder's other `v-<V>`) whose hash is the manifest's is written as that shader's result file (`"reused": <its version>` in the head, its entry, bindings, c1 and stored modules as they were), newest library first. Only the rest is translated. The vertex shaders' padding takes a kept pixel shader's inputs from its base module. `write_library` writes a kept entry's bytes as they are, so the library is the full build's byte for byte. `progress <done> <total>` counts the shaders translated (`total` = all less the kept ones; the progress file has `reused` too), and `delta: …` lines say what was kept from where.
- **Check.** At the end every entry of the new library is hashed (stage `check`) and compared with the manifest, for the keys the manifest has: a mismatch, or a shader the manifest has and the library lacks, is one `[RED] delta check: <key>: …` line with the reason and whether the entry was kept or translated; a line `delta check: <n> of <total> shaders as the manifest has them` closes it. The library is kept (it is what this machine's tools made). A full build with a manifest of its version checks the same, so a phone's full build is compared with the Mac's.
- **Play while it runs.** The library header carries `abi` (`DMSH_VK_ABI`, `dmsh_chain_vk.h`): the hash of `dmsh_abi_vk.h` and `dmsh_abi.h` without comments or blank space, which includes `DMSH_VK_ABI_REV` (raise it for a convention between the modules and the replay that neither header shows). The replay loads its own version's library; while that is missing from the pack, it plays the newest other `v-<V>` of the pack whose header names the game and carries the host's `abi` ([What the replay does](#what-the-replay-does)), and the launcher keeps Play on for the same rule (`ShaderLibs.playable`). Failing that, a library of an older ABI that the host still plays: `dm/gfx/vk_android/vka_abi_compat.h` lists such ABIs, each with what its modules do otherwise, which the replay then follows (`674db0a4ff79`, before a319e773: the raw global memory write log is the page-hash set, bound and read as such, `vka_gml.h`); the launcher gets the list as `NX_DMSH_VK_ABI_COMPAT`. The file is not in the digest, so a row moves no version; its rows are for the host ABI it names (`VKA_ABI_COMPAT_FOR`) and are used only while that is the tree's, so a moved ABI means checking each row against the headers' diff again (and adding a row for the ABI just left, if its modules can be followed) ([An older library of another ABI plays while the update runs](../docs/reference/shaders.md#an-older-library-of-another-abi-plays-while-the-update-runs-android)). A library made before the field (`66d1dd2cd5ff` and older) has no `abi`, so whether the host reads it the same is not known: it is the last resort, never a block. When the pack has no library of the host's version or ABI, the replay plays the newest such one with a `[RED]` warning that it may draw wrong (`vka_shader.c lib_load`), and the launcher keeps Play on, says "Ready · shaders need one update" with a chip and a toast explaining it, and suggests updating the shaders once more (`ShaderLibs.legacy`, `LEGACY_WARNING`); after that update, later ones are deltas of the same ABI. (For DKB the release `66d1dd2cd5ff` has the same modules as `6607c8d19abc`, so it draws right.)

The launcher's states for a pack whose library of this APK's version is missing (`Pack.libraryProblem`): (a) no library at all, or (b) only one of an ABI the host does not play: when the shader layer covers the game (a Switch 2 title, `DM_VK_LAYER` not 0 in the player's lines for it: `ShaderLibs.layerCovers`, `Pack.shadersOnDemand`) Play is never held back: the card says "Ready", the game starts with no library and the layer builds what it asks for ([Shaders the library lacks](#shaders-the-library-lacks)), and Prepare shaders is an optional small row on the game's page (dismissible, `GameSettings.shadersOnDemandRow`; also under Storage › Prepare again) for the player who wants the whole set. For a game the layer does not cover (Maxwell, layer switched off, no folder the layer can be written to) Play waits as before, the card says "Shaders needed", its Why? says what keeps the layer off, and Prepare makes the library ([Launcher states for shaders](#launcher-states-for-shaders)). (c) A library of this APK's own ABI (or an older one the host follows, or one without an ABI field) plays meanwhile: with a delta manifest row for it the update starts by itself in the background ("Ready · updating shaders"; pausable, Play stays on) when it is small, at most a quarter of the set (`ShaderLibs.autoDelta`, `Pack.deltaAutomatic`), and is offered on the game's page like an update with no manifest when it is larger ([Optional shaders](#optional-shaders)); without one the game's page offers it, as a small dismissible row: for a game the shader layer covers (`Pack.shaderLayerFills`: a Switch 2 title, the layer not switched off, a folder it can be built in) "Shaders: older, built while playing" whatever the older library's ABI or inputs digest (the words say that the shaders it has stay as they were made when the inputs differ, `PrepareText.olderLayerText`; [Shaders the library lacks](#shaders-the-library-lacks)), else "Shaders can be updated". No big card stays on the page, and Play is never held back by an older library the host plays. (d) A library of this version with the profile's inputs: nothing. A library of this version made from other tables is not played as an older one: the host loads it, and its keys may hold other shaders, so it stays "Shaders needed".

Measured on the Mac (DKB, 2026-11-04, version `6607c8d19abc`): see [the simulation](#delta-update-simulation-2026-11-04).

### Restamp

When a new version's library equals an older one byte for byte but for the header's version (`vk_chain`) and `abi`, the update needs no job at all. `--publish-delta` with that older library writes a `stamp` row into the manifest: `stamp <older version> <SHA-256 of the older file> <SHA-256 of this version's file>` (`vk_android_delta.py stamp_only`; byte-identity is the rule: a shader that builds in neither counts in the `from` row, as MKW 1.8.0's one does). The APK carries the rows (`Profile.stamp`, a column of `NX_PROFILES`). When a game card is checked and its pack has no library of the APK's version, `ShaderLibs.restamp` takes an older library of the pack whose SHA-256 is a row's first hash, copies it with those two header fields rewritten (`restamped_header`) into `shaders/.restamp-<V>/` with its `inputs.tsv`, and moves it to `shaders/v-<V>/` only when the copy's SHA-256 is the row's second hash: the Mac's library of this version. That takes seconds (one copy, two hashes), with no split and no translation; the older library stays. A library made on the phone by the same tools is the Mac's byte for byte, so it qualifies too; a damaged or different one does not, and updates as before. A later version whose shaders change gets no `stamp` row: phones then update by delta as usual, so the carry-over ends by itself.

First use, 2026-11-04 (tools digest `44b34b6f8f94` kept at version `6607c8d19abc`, `vk_android_same.tsv`): the release library `v-66d1dd2cd5ff` and `v-6607c8d19abc` differ in 22 header bytes only, for DKB (364,249,307 bytes) and MKW 1.8.0 (167,573,823 bytes), so APKs of `6607c8d19abc` take a release pack's shaders over without an update.

The Vulkan tools are not among `DMSH_CHAIN`'s files, so adding or changing them does not move the Apple libraries: they stay byte-identical, in the same `b-<V>/`. The translator is the vendored `dmsh_xlate_bin` checked against `dmsh_chain.lock` (only its half of the lock: the Metal compilers are not needed). The build reads control sections and makes the translator's jobs with `dmsh_build.py`'s own functions (`job_for`, `vertex_ab`, `tf_layout`, `decode_tex` and the other handle decoders), taken from that file's source by name, so they stay one copy.

### Sampled keep

**Status 2026-11-16: on by default.** The check runs for every game whose pack is a candidate; `DM_SHADER_SAMPLE=0` in the player's lines for a game switches it off (`ShaderLibs.SAMPLE_ON_BY_DEFAULT`). A player's pack holds the whole library (some 40,000 shaders), so 300 drawn shaders are cheap next to a full build. One check runs at a time (`SampleQueue`); Play takes the lead and pauses it, and it never blocks another card.

**Resolved 2026-11-16: Play waited for the check.** The launcher's stop (Play) is a `KeyboardInterrupt` that lands between translator calls, and the check translated 64 shaders a call (`DMSH_VK_BATCH`'s default): on a warm phone one call took about 50 s, and the game's own layer build was refused meanwhile (`layer build waits: a build runs`), so OoT stood at a black screen until the test's stall watchdog ended it. The check now translates 16 a call (`shader_sample.BATCH`; a `DMSH_VK_BATCH` line wins), so a stop lands within seconds. On the phone, OoT's 0.3.26 library was declined (185 of 445 checked entries differ; the Mac's run of the same library 264 of 511), as it should be.

**Resolved 2026-11-16: the check "hung" because Android froze its process.** `LayerService` was a plain started service. About a minute after the launcher left the screen (Home, the screen off, another app in front), Android stopped it (`ActivityManager: Stopping service due to app idle … LayerService`). The `:pack` process then had no running component, became cached (oom adj 905) and was frozen (`HnFreezerController: freeze pid=… reason=AOSP`, `cgroup.freeze` 1) with the tool mid-run: CPU time stood still, no stack was dumped (faulthandler's thread is frozen too), and the packer's lock stayed held. The check now runs as a foreground service (`dataSync`, as Prepare's `PackService`; `Ondevice.startSample` calls `startForegroundService`, a notification "Checking shaders" shows while it runs, `onTimeout` stops it without a verdict). A start the service refuses no longer calls `stopSelf(startId)` while a check or build runs in it. A layer build is not affected: it runs while its game is in front, which keeps the app's uid active. Phone test after the fix (OoT, launcher sent Home 20 s in): the check kept running past the minute at oom adj 200 (foreground service), with only the vendor's short 3 s pauses (`HnFreezerController … reason=IAWARE_FAST`). **Open (vendor):** on the test Honor phone PowerGenie still froze the foreground service when the phone was briefly unplugged and folded (`freeze … reason=PG`; it stays frozen until the app is opened again), as it freezes every background app the user has not exempted from battery optimization; Prepare's `PackService` is exposed the same way. A fix there is an exemption the player grants (Settings › Battery › app launch, or `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`): not done.

When a version of the tools has no delta manifest, no stamp row and no Mac library (a full Mac build of every game was not made), a pack that has an older library, its game's dump or `.nup` and the profile's inputs asks whether the older library would be the same with the new tools, before any full build is considered (`dm/gfx/tools/shader_sample.py`; not one of the chain's files, so no library version moves). The older library is of this ABI, or of an older ABI whose row in `vka_abi_compat.h` differs in nothing (`NX_DMSH_VK_ABI_SAME`; today `228b73bd10f6`, which every 0.3.26 pack holds): the sample compares the new tools' entries with the library's own, so entries that come out identical are what a library of this ABI holds, and the stamp then sets the ABI. An ABI whose row has a difference bit (`674db0a4ff79`) is never stamped this way.

- **The queue and its cards** (`SampleQueue`, `Ondevice`, the tile ring and the game page card (`GameSettings.shaderCheckCard`); JVM test `SampleQueueJvmTest` through `test_android_samplequeue.py`). A pack joins one process-wide line when its card is evaluated, has a candidate and no verdict; one check runs at a time, in the order of the line, never beside another check, a Prepare job, a layer build or a game. A start waits while a game runs, the packer is busy, the app is under 20 s old (`SampleQueue.SETTLE_MS`: opening the launcher starts no work at once) or the phone is not calm (`LayerWatch.verifyCalm`: no pause, no warm note), and after a refusal for 30 s. A pack is marked tried (not asked again until the app restarts) only after its check ran and ended, with any verdict, or after it failed to start three times; a start the packer or the phone refused (`refused.txt` in the work folder, written by `LayerService`) marks nothing. A check given up after three failed starts is also recorded on disk, as a Skip is (below). Each pack in the line has a card at its game's place, as Prepare's card: the running one says "Checking shaders" with a bar and its counts (`progress.json`, written every 3 s by `shader_sample.py`: the requests read from the game's files first, then the translation; before the file exists the log's `seed N M` lines), the others "Waiting to check shaders (n ahead)" ("next" for the one after the running check), with Play and Skip; the other cards, Prepare, Play and the game pages stay usable. Skip removes the pack from the line and the line goes on; it is recorded in `shaders/.sample-skip-<V>.json` (`why` skip or failed, `at_ms`, the APK's version and commit, the check's counts: no keys; `SampleQueue.skipHolds`), and the pack is not queued again until the APK or the tools (`<V>`) change or 7 days pass (`SampleQueue.SKIP_MS`). **Play takes the lead:** starting any game stops the running check at its next safe point (`LayerService.EXTRA_STOP` interrupts the tool after the shader in hand; `shader_sample.py` exits 12 and writes no verdict), puts it at the front of the line and starts the game without waiting; no check runs while a game runs, and the line goes on by itself after it (a 20 s hold covers the game's start); the stopped check itself resumes, after its backoff (below). A pack whose check is accepted gets the toast "Shaders up to date"; a declined check says nothing new (the pack is updated the other ways).
- **Resume and backoff (2026-11-16).** Before, only a verdict outlived the process: a check ended by Skip, by Play, by closing the app or by a refusal left nothing, so every app start queued the pack again and translated its ~300 shaders from zero (on the test phone only OoT had a verdict). Now a check that is stopped (exit 12) or killed keeps its translations in the work folder `shaders/.sample-work/` (`layer/`: the requests and the layer's one result file a shader) with `resume.json`, the run's key: the older version, this version, `DMSH_CHAIN`, the profile's inputs, the ABI, the game file (its path, size and time), the sample size, the starter share, the seed and a digest of the drawn keys (`shader_sample.resume_key`). A run with the same key keeps them (the requests written are not read again, a shader with a result is not translated again: `shader_layer.py`'s results) and logs `sampled keep: resuming, R of T shaders translated by an earlier run that was stopped`; any other key starts afresh. The seed is no longer random: `shader_sample.stable_seed` (game, older version, `DMSH_VK_CHAIN`, `DMSH_CHAIN`), so a rerun draws the same sample; `DM_SHADER_SAMPLE_SEED` still wins. A stop writes `stopped.json` (`at_ms` and counts). An interrupted check (Play, the app closed or killed) is not started again until 10 minutes after the interruption (`SampleQueue.BACKOFF_MS`; `interruptedAt`: the stop's time, else the newest of `progress.json`, `resume.json` and the marker), besides the usual settle time; meanwhile its card says "Waiting to resume shader check" with "Resumes in about N min", and the line starts the next pack that is ready (`SampleQueue.startNext(ready)`). A pack with no history waits only the settle time. A resumed run's card says "Resuming shader check" (`progress.json` has `reused`). A verdict removes the work folder (`clear_resume`, then `LayerService.sample`).
- **Known transitions (2026-11-16).** Some chain bumps are known to change the library's entries only in ways with no visible effect. They are rows of `dm/gfx/vk_android/vka_known_transitions.tsv` (`<old VK chain>`, `<new VK chain>`, what the diff found), keyed on the older library's header version field (its VK chain as stamped; not its `DMSH_CHAIN` field: OoT's 0.3.26 library was stamped forward and still says `1cf10a4252df` there). A sample candidate whose pair is a row is kept with no check, no card and no translation, and it is **moved, not copied** (user decision 2026-11-16: no extra space): `Ondevice.knownKeep` / `ShaderLibs.knownKeep` write a journal (`known-move.txt`: the older version and its three header fields) into `shaders/v-<old>/`, rename that folder to `shaders/.known-<V>/` (one rename in the same folder, so one file system), rewrite the header's version, abi and chain fields in place (128 bytes, synced), write the marker `sampled-keep.json` last (`kind` `known-transition`, `old`, `from_chain`, `version`, `sample` 0), rename the folder to `shaders/v-<V>/` and write an accepted `.sample-<V>.json`; `inputs.tsv` moves with it unchanged (it holds the game and inputs, no version). The toast says "Shaders up to date". A first rename that fails leaves the older library where it was (nothing is copied; the log says why); a later failure puts it back, header restored. A crash after the first rename leaves `.known-<V>/`, which neither the host nor the launcher takes; the next evaluation of the card finishes the move from its journal (`ShaderLibs.knownRecover`), or puts the older library back when the pack has a library of `<V>` meanwhile. **The older library is gone afterwards:** an older APK of that chain (0.3.26 for `65883461079b`) finds no library of its own in the pack and updates it again (its delta or a full build). Only a library whose header holds the table's old VK chain is moved, never another chain's. The APK carries its own chain's rows (`BuildConfig.NX_KNOWN_FROM`, `build.gradle` `knownFrom`); `shader_sample.py` reads the same table (`known_transitions`) and keeps such a library without a sample too. The host treats it as any kept library, so the layer verifies what is played and its entries win where they differ: that is how the few changed entries heal. Any other pair goes through the sampled check. The one row today: `65883461079b` (0.3.26) to `19662e4c4a25`, from the 2026-11-16 entry diff of OoT's sample (equivalent raw-gmem vector loads, sin/cos argument reduction, `LEA.HI.X.SX32` sign-extend, 3 rare mesh/compute entries; interface, bindings and padding identical, so old and new entries mix safely). **Adding a row** on a later chain bump: only after a diff investigation of the two chains' entries (as that one: the sample's differing entries disassembled and classed) shows that every class of change has no visible effect and the interface, bindings and padding are identical; the note column says what it found. The table is no chain file (no library version moves); a test checks its format and the row.
- **The check** (`LayerService.sample`, started by the line as a foreground service; 300 shaders with their mates, a few minutes on a phone). `LayerService` runs `shader_sample.py`: it translates at most `DM_SHADER_SAMPLE` shaders in all (default 300, `0` turns the check off; the player's lines for the game), a vertex shader counted with the pixel shaders paired with it, drawn from the older library (`shader_sample.draw_capped`; before 2026-11-16 the 300 counted the drawn keys only, and OoT's came to about 1,000 shaders with their mates, 8 minutes on the phone). The first `DM_SHADER_SAMPLE_FIRST` of them (default 200) are the game's starter set (`dm/games/<id>/shader_first.tsv`, in its order, the keys the older library has and the game's RomFS holds: the shaders a start uses first); the rest are drawn at random from the others (all of them for a game with no starter set), stratified by stage and by size class (under the median, the median to the 90th percentile, the top tenth: each stratum gets a share of the square root of its size and at least one, so the rare stages and the large shaders are in), with a seed that is logged and recorded (stable for an older library and these tools, see Resume; `DM_SHADER_SAMPLE_SEED` sets another). A vertex shader is taken with every pixel shader paired with it (its entry is padded for them; one with more than 200 mates is left out), and the keys are taken in order, each with its mates, while the total stays within `DM_SHADER_SAMPLE`: the starter part first, in its order, then the random part in an order shuffled by the seed, so the random part is cut first and then the starter set's tail. The log line says what was taken: `sampled keep: seed S, F from the starter set, R random, T in all with the pixel shaders paired with the vertex ones (at most 300), of L shaders`. The requests are written from the game's own file (`shader_seed.py`) and translated as a layer is (`shader_layer.py`), so each entry is the one a full build makes, and each new entry's hash (`vk_android_delta.entry_hash`) is compared with the older library's entry for the key. Only a library of the game, of this APK's ABI and of the profile's inputs is a candidate (`ShaderLibs.sampleCandidate`: the update would be optional and the layer covers the game).
- **All the same:** `Sampled keep: N of N shaders identical`. The older library is copied to `shaders/v-<V>/` with its header's version, abi and chain set (as [Restamp](#restamp)), with its `inputs.tsv` and the marker `sampled-keep.json` (old version, sample size, requested, seed, mismatches 0, date); the older one stays. The card is "Ready", the toast "Shaders up to date"; the game page says nothing about the library's age.
- **Any difference:** nothing is taken over. The result is written to `shaders/.sample-<V>.json` (counts only, never keys) so the check is not asked again for that older library, and the update goes on as before (the delta with a manifest, else the layer fills; the full build stays the page's button). Too few shaders found in the game's files (under half the sample) is not a verdict: nothing is kept.
- **Verify what is played.** The host reads the marker once at the load (`vka_shader.c` `g_kept`) and, for a kept library, asks the layer for every program it resolves (once a program, never per draw) and takes the layer's entry of a stage when the layer has one. `LayerKept` (the launcher) tells these requests from missing shaders: they are not counted ("Building shaders (N)" does not show them), the start does not drop them (`LayerGuard.dropCovered`), an ordinary run does not build them (`shader_layer.py --kept`, `split_requests`), and `LayerWatch` asks for a verify run (`--kept --verify`, 32 shaders at most, one worker) only when nothing is missing, the phone is calm (`verifyCalm`: no pause, no warm note), the game has run two minutes and a minute has passed since the last one. After each run `shader_sample.record_verify` compares the new layer entries with the kept ones and writes `lib/v-<V>/verified.tsv` and `verify.json` (`{"verified": n, "mismatched": m}`: counts only, for the game page, which has nothing to say about them). A differing entry stays in the layer's library, which wins over the kept library's in the host; a program resolved before the layer had it keeps what it had until the next start.
- **What it proves and does not.** The starter set's identical entries show that the shaders a start uses first are the same. The random part's N identical entries show, with 95 % confidence (3 / N: about 1 in 33 at N = 100, 1 in 100 at N = 300 with no starter set), that fewer than that share of the library's entries changed; a rare change that no draw hits passes. With the cap the random part can be small or none (a starter set whose vertex shaders have many mates fills the 300 by itself), and then the check speaks for the starter set only. The verify step is what covers it for the shaders the player actually reaches, once played; shaders never played are never checked. It does not prove the library byte-identical to a full build (the delta manifest's check does), only that the new tools make the same entries for the sample. A change in how a vertex shader is padded for pixel shaders the sample did not include is possible in principle; the sample includes each drawn vertex shader's mates. The user accepted the risk of the heuristic. If a release changes the translator on purpose, publish its delta manifest or make the library on a computer: a sample that finds differences declines by itself.
- **Open:** the check has run on a phone (OoT, declined; the starter-set draw seen in its log), the queue's other paths and cards not yet (the sample's time, the stop at the shader in hand, the bar's counts, the layer's heap cost: every played shader's entry is copied once the layer holds it, about 9 KB, not only the differing ones; the host edit is compiled with the NDK only). Tests: `test_shader_sample.py` (the draw, the comparison on synthetic libraries, the verify counts, the request split), `test_android_layer.py` (`LayerKept`, the kept library is not dropped), `test_android_shader_delta.py` (`sampleCandidate`).

### Selected shaders

A profile may list the shaders its game needs in `dm/games/<id>/shader_seen.tsv` (rows `key<TAB>stage`; column 4 of `shader_map.tsv`), when its map is far larger than what play reaches (0400A3A01EE4C000: 8,157 of 131,426). The phone's shaders step, and `scripts/pack_android.py` on a computer (`selected_keys`; on Windows through `vk_android_win.py`'s `@<file>`), then build only those: `PackService` passes the set's keys that the map has (`ShaderLibs.selection`, sorted, each once) after the two folders, and `vk_android_build.py` adds the pixel shaders paired with them (`build_keys`), as the Mac's partial build takes them ([Building selected Mac shaders](../docs/development.md#building-selected-mac-shaders)), so the phone's library is the Mac's. The step's log names the keys by count. The phone's split (`DM_SPLIT_SELECTED=1`) then keeps the code of only those shaders and their pixel shaders: the others get empty records, the tables are a full split's, and `pkg/selected.txt` lists the kept keys (a step whose selection needs others splits again; [A shader split that keeps every shader's code in memory](../docs/reference/memory.md#a-shader-split-that-keeps-every-shaders-code-in-memory-android)). An empty record has no key, so a split of another build of the game, whose records `vk_android_build.py` finds by key, skips them; with Try anyway (`DMSH_VK_REQUIRE_ALL=0`) a selected shader that build lacks is left out with one `[RED]` count instead of stopping the step ([The shaders step crashes at once on a game build the profile was not made from](../docs/reference/packing.md#the-shaders-step-crashes-at-once-on-a-game-build-the-profile-was-not-made-from)). `DMSH_VK_REQUIRE_ALL` holds for a selected build too. The launcher's count (`Profile.shaderTotal`, gradle's `shaderTotalOf`) is the same set with its pairs from the profile's `shader_pairs.tsv` and `pso_pairs.tsv`, so Prepare's time and the progress bar are the selection's. Any profile with the file gets this; one without builds its whole map. A key-list build takes the profile's [delta update](#delta-updates) as a full build does: it keeps an older library's entry whose hash is the manifest's, translates the rest and checks at the end, and the profile's manifest is published from the Mac's build of the selection (`--publish-delta` checks it holds exactly the selection and its pairs), with its `from` and `stamp` rows ([Restamp](#restamp)). An entry's hash is the key's alone once the tools and the profile's inputs are fixed (`shader_seen.tsv` is not one of the inputs), so a manifest of another key set serves the keys it has (`vk_android_delta.py coverage`): when the selection changed after the manifest was published, its new keys are translated and not checked (`delta: <n> of the <m> shaders of this build are not in the manifest`), its dropped keys do not count, and only the manifest's `-` keys excuse a failure; the APK then takes no `from` or `stamp` rows from it (`build.gradle` `deltaCurrent`: the manifest's keys must be the ones Prepare builds). The phone's split keeps only the selected shaders' code, which is all a delta needs: a kept entry needs no code. A pair from the split's `pso_pairs.tsv` that the profile lacks (not one of the inputs) can make a vertex shader's entry differ from the Mac's; the check names it. The library has no `inputs.tsv`: the pack step stamps it from its header (`pack_android.py lib_stamp`). `DMSH_VK_REQUIRE_ALL` does not apply to a key list, so a shader that fails leaves the library without it (the `[RED]` lines in `shaders.log` name it) instead of failing the step.

### Shaders the library lacks

A game that asks for a shader its library lacks (a selected set that play went past, or a shader of a game that is not in its map) draws nothing with it: the log has `[RED] vk: shader <key> (program stage N) is not in the shader library` (the first 32). Since 2026-11-15 the host notes each such key once (`vka_shader.c` `miss_note`): a log line `[shaders-missing] <key><TAB><stage>` (the game's log, so a log attached to an issue carries the list) and a row of `$DM_TEMP/missing_shaders.tsv` (`files/temp/<title ID>/`, rows `key<TAB>stage` like `shader_seen.tsv`, kept across runs, each key once). The stage is read from the control section and the SPH as `shader_split.py` does (`?` when the code cannot be read). Nothing is sent anywhere: a list travels only when a player attaches the log or the file to an issue.

- `python3 scripts/issue_digest.py <issue>` ends with a "missing shaders" section (count and keys per game) for every log of the issue.
- `python3 scripts/shader_harvest.py [path ...] [--apply]` reads those lines, the `.tsv` and the older `[RED]` lines of logs under `$BN_ISSUES_DIR` (or the folders named on the command line) and, for a profile that has a `shader_seen.tsv`, appends the keys that are in its `shader_map.tsv` and not yet listed (`--apply`; one `# Added later` comment, each key once). A key outside the map is reported and not added. Selected sets are shipped as `shader_seen.tsv` says, so a harvest followed by the Mac's partial build of the new keys (`docs/development.md`, Building selected Mac shaders) and `--publish-delta` is how a set grows; a set can also shrink to the harvested keys once enough lists have come in.
- `dm/gfx/tools/shader_layer.py --game <id> --root <folder> --build` builds requests into a library of their own (a layer), without touching the prepared library: the requests are `<key>.ctl` / `<key>.code` files in `<folder>/req/` (`DM_NVN_SHDUMP=<folder>/req` writes them at a miss), optionally a `pairs.tsv` (vertex key, pixel key). The tool makes a package of the records and a temporary profile (the game's own with a `shader_map.tsv` of the requests: `DM_GAMES_DIR` + `DM_GAMES_FIRST`), and runs `vk_android_build.py` on them, so a layer entry is the one a full build makes of that shader; results are one file per shader, so a rerun builds only the new ones. The result is `<folder>/lib/v-<DMSH_VK_CHAIN>/dmsh_vk.lib`, a library of the game's format that `DM_VK_SHLIB` can name.
- **Where the layer lives.** The pack's `shaders/layer/` (`LayerDir`), which the launcher gives the host as `DM_VK_LAYER_DIR=<pack>/shaders/layer` (the host's fallback without it: `$DM_TEMP/shader_layer`; the launcher leaves the variable out and uses that one only when the pack folder cannot take the folder). It holds `req/`, `layer.log` and `lib/v-<DMSH_VK_CHAIN>/` (the library, its `results/`, `layer_state.json` and that version's `built.tsv`), so what was built stays between runs and a game with no library keeps what it built so far. It is not a temporary folder: Storage lists it on its own, "Shader cache built while playing" (`StorageScan.Kind.LAYER`, off by default, deletable; it is rebuilt as you play), and never deletes it with "Game temporary files". A layer an earlier version kept in `files/temp/<id>/shader_layer` moves to the pack's when the pack has none yet (`LayerDir.resolve`). Each version keeps its own build list, `lib/v-<V>/built.tsv` (`LayerPending.builtFile`, `shader_layer.py built_path`; the older shared `built.tsv` at the folder's top counts only for its rows of the version asked, until that version has its own), so a new version builds the requests in `req/` into its own library, and two apps of other versions sharing a picked pack folder (the test app and the play app) do not settle or undo each other's. At each start `LayerDir.tidy` removes another version's folder whole (library, results, build list) only when no app has touched it for 30 days, or when the whole layer folder is past this version's quota (the oldest first until it fits); never while a build's marker is fresh. `DM_VK_LAYER_DIR` is one of the paths the launcher sets (a player's line for it is refused, as `DM_TEMP`'s). Prepare must leave `shaders/layer` alone.
- **While the game runs (Android, `DM_VK_LAYER`, default on).** For a program with a shader the library lacks the host writes each of its stages as a request (`<layer folder>/req/<key>.ctl` and `.code`, from `nvn_prog_ctl`, the control section copied at `nvnProgramSetShaders`, and the code from guest memory; `pairs.tsv` has the program's vertex and pixel keys). The layer folder is `DM_VK_LAYER_DIR` when set (the launcher may keep it in the pack, so the layer outlives a clear of the game's temporary files), else `$DM_TEMP/shader_layer`; with neither, or `DM_VK_LAYER=0`, there is no layer. The requests are copied on the render path and written by a thread of their own (`vka_layerreq.h`: each key once a run, a queue of at most 256 requests or 64 MB; an earlier run's `.ctl` is not written again). A key is marked when its request is queued; a stage or pair the writer cannot write (the disk full, the folder removed by Storage while the game runs) is handed back and unmarked, the folder is made again at the next request, and the log has `[RED] vk: shader layer request <key> not written: <reason>` (the first 16). A request the queue refuses, or one the writer could not write, is asked again without waiting for a new layer: the cached programs that lack a shader are resolved again at the next poll once the queue is at most half full, and after a write failure 1 s later, the wait doubling up to 64 s while writes keep failing. The key set holds 16,384 keys a run; past that a key is not marked, and a stage whose `.ctl` is on disk is not copied again (one stat). Every program that takes a stage from the layer (it lacks one in the prepared library) asks for the stages the layer lacks and records its (vertex, pixel) pairs, each pair once a run (a bounded set of 16,384) and also when every stage was asked for before (a request of pairs only); the writer reads `pairs.tsv` once and appends a pair it does not hold, ending a last line an earlier stop cut short first. A request of pairs only starts no build by itself (`LayerPending` counts `.ctl` requests, not pairs); the next build, which takes every request and pair, uses it. `LayerWatch` (the game's process) counts the requests that `built.tsv` does not settle, shows "Building shaders (N)" at the top middle, and starts `LayerService` (the packer's process, `:pack`, so the Python is loaded once; not while a Prepare job exists: `PackLock`, below; every 5 s while requests are pending, every 30 s after a run that settled none, never while the service's marker `.building` is fresh, and it stops asking after 5 runs in a row that settle none), which runs `shader_layer.py --build` in the interpreter (`run_build`: `vk_android_build.py` in process, the phone may not start programs) and writes `lib/v-<V>/dmsh_vk.lib` and `lib/v-<V>/built.tsv`. The host polls the file once a second (`vka_layer_poll`, from the present path): a changed layer is mapped as a new one and the cached programs that lacked a shader are resolved again (`vka_layer_gen`, `g_pm` in `vka_draw.c`, `g_pr`), and an entry of the prepared library wins over the layer's, except in a program that has a missing shader: its other stages come from the layer where it has them (the layer's vertex shader is padded for the program's pixel shader, the prepared one is not). The draw is skipped until the layer has the shader, as a pipeline is with `DM_VK_PSO_ASYNC`.
- **A layer's lifetime.** A shader made from the layer keeps its own copy of its entry (`vka_shlib_extract`: the entry, its bindings, module records, c1 bytes and stored modules, as a one-entry library on the heap; about 9 KB a shader on DKB's layer, 17.7 MB for 2,053), and the shader table finds it by key and entry hash (`vka_shlib_entry_hash`, the pipeline cache's), not by the layer it came from. So a rebuilt layer whose entry for a key is byte for byte the same (the packer rebuilds every layer from the same result files, `carry_results`) gives the same shader object, modules and pipelines; only a new or changed entry makes a new one. No shader points into a layer mapping: a lookup holds the current layer by a reference (`vka_ly_get` / `vka_ly_put`, `vka_layerreq.h`), and a replaced layer is unmapped when its last lookup gives it back, which frees the disk space of the file the packer replaced (before, every replaced layer stayed mapped until the process ended: several GB after many rebuilds). The log line of each new layer says how many layer mappings there are and how many replaced ones were unmapped. Limits: the copies are heap memory the system cannot page out (the prepared library's pages can be), about the layer's size for the shaders made; a program resolved before a rebuild keeps the shader object it had even when the new layer changed that entry (it is not resolved again unless it lacks a shader); a pair recorded only by a program that lacks no shader is lost for the run when the queue refuses it (it is recorded at the program's next resolution).
- **The pipeline cache's stamp.** `vka_shader_lib_id` names the library played for the cache file's stamp (`vka_pso.c`, `vka_pckeep.h`), read once when the cache opens at the start. With a real library it is the hash of its header, as before (the layer's shaders are not listed). With no library the empty header is the same in every run, so the stamp never changed while the layer grew and the cache file was read whole each start, holding the pipelines of layer entries rebuilt since (Turnip loads every object of a cache file it opens); now the id hashes the layer's header after the empty one (its inputs digest, entry count and blob size change with every build that adds or rebuilds a shader; with no layer yet, the empty header alone), and the stamp lists the layer's shaders this run made with their entry hashes (`vka_shader_made`, `vka_shader_content`, with the layer an earlier run left, which `lib_load` maps before the cache opens). A start whose layer changed then keeps the file when most of the shaders it lists are the same in the layer (`DM_VK_PCACHE_KEEP`) and counts the changed ones stale, rather than throwing the cache away. A layer mapped while the game runs does not change the run's stamp: only the next start compares.
- **No library at all.** A pack with no `shaders/v-<V>/dmsh_vk.lib` and no other version the host plays (same ABI, a compatible older one, or one without an ABI field) still plays when the layer is on: `lib_load` takes an empty library of the host's own header (`vka_shlib_empty`: no entries; chain, Vulkan chain, game and ABI the host's; the translator answers `DMSH_VK_SUBGROUP_SIZE` and `DMSH_VK_SSBO_ALIGN` the layer is built with, so the subgroup plan is the layer's), with one `[RED] vk: no shader library at … playing with an empty one` line. Every key is then a miss: noted, requested, its draws and dispatches skipped until the layer has it, so the first minutes draw little while the packer builds. An earlier run's layer is mapped at once when the empty library is taken (not at the first poll), and the prewarm threads take their shaders from the layer (`vka_shader_by_key`); with a real library they take only the library's, as before. A real library, when there is one, plays as before (its entries win; the layer only fills). With the layer off the log keeps `[RED] vk: no shader library at … nothing is drawn`. A layer whose subgroup size differs from the playing library's (the plan was made for that one), or whose storage-buffer alignment the device cannot bind, is refused with a `[RED] vk: shader layer … not used` line.
- **Missing compute shaders.** A dispatch whose compute shader is missing is skipped (no wait, nothing recorded), so what later work reads from it may be wrong until the layer has the shader; one `[RED] vk: compute shader <key> missing: its dispatch is skipped until the shader layer has it` line for each of the first 32 keys a run, then a count at every 1,000th (`miss_compute`). Compute programs are resolved again when the layer grows, as draws are (`resolve` and `g_pm` serve both; `vka_layer_poll` drops the cached programs that lacked a shader). Draws and dispatches skipped for a missing shader no longer count as the device's skips (the skipped-work notice, `vka_skipwarn.h`): the shader is the pack's, not the driver's.
- **Safeguards.** (`LayerGuard`, plain Java; `LayerPending`; tests `test_android_layer.py`, `test_shader_layer.py`)
  - *The player's switch.* Game settings › **Shaders while playing** (`Prefs.layerBuild`, per game, on by default; on the game's page in the on-demand row and in its Advanced section; Settings › Advanced's `DM_VK_LAYER` row is a link to it). Off: the host gets `DM_VK_LAYER=0`, no watcher runs, and the rules that decide Play read it (`Prefs.layerEnv` adds `DM_VK_LAYER=0` to the game's lines for `ShaderLibs.layerCovers`), so a game with no library is "Shaders needed" again.
  - *Requests the prepared library has.* At each start `LayerGuard.dropCovered` removes the requests whose key the library the host plays has (`ShaderLibs.hostLibrary`: this version's, else the older one it plays): one built on a computer was moved into the pack, or Prepare finished. It reads the library's header and binary-searches its sorted entries, so it costs a few reads a request. A library is taken as the host's only when the host would take it: `ShaderLibs.structureProblem` does `vka_shlib_check`'s structural checks in Java (the entry, binding and module tables and the blob inside the file, then every entry and module record), so a library cut short (the host's "blob out of the file") is passed over as the host passes it over (the next library it plays, or the empty one with the layer), and its keys are never dropped from the requests. A request stays when another stage of its program (`req/pairs.tsv`) is missing from the library: the host then takes the program's stages from the layer.
  - *Quota.* What counts is this version's part of the folder: the requests, the folder's own files and `lib/v-<current>` (`LayerGuard.usage(layer, version)`, `shader_layer.py layer_bytes(root, version)`); other versions' folders (an older APK's after an update, or the other app's) never count, since the host maps only its own version's, so an update never leaves a game stopped by the older layer. The quota (`LayerGuard.quota`) is room for a whole layer of its library (the library, its results, about 2.2 times it, and the next library written beside it: 4.5 times the library), at least 2 GiB, and never so much that the volume keeps less than 1 GiB, or a twentieth of what the layer can have, free; a growing layer is so stopped by the phone's free space, not by its own size. The watcher measures it off the main thread at most once a minute; past it, it asks for no build, says "Shader build paused (storage)" (the panel's line: "paused (storage: free space on the phone, or Import a library on the game's page)"), logs one `[RED]` line a run and leaves the note `.quota` in the folder, which the game's page reads (checked against the free space then): its shaders row says why nothing more is built and the ways forward (free space, Import a library, Build all for a game the phone can prepare, Storage › Shader cache built while playing) and is not folded away (`LayerStatus.storageText`). `shader_layer.py --max-bytes` (passed by the service) refuses to build past it as well (exit 3). The host keeps writing request files (small: about 15 KB a shader); stopping those is the host's part (open).
  - *The build's marker.* `LayerService` makes `.building` in the folder as a build starts, touches it every 30 s from a thread of its own while the build runs (`LayerPending.BEAT_MS`), and removes it at the end; it counts while touched in the last 3 minutes (`BUILDING_MS`). However long a build runs (batches grow with what is built), the watcher neither asks for another run nor counts an empty one, and a game's start does not take its library being written for a stopped build's; a killed `:pack` leaves a marker that stops counting within 3 minutes for an other app, and at once for this one: the service writes its pid and package into the marker (`LayerPending.markerText`), and the game's start (`GameActivity`, then `LayerWatch.start` and each tick) removes a marker of this app whose process is gone (`LayerPending.clearStale`: a force-stop mid-build no longer holds the next start's build for minutes, 2026-11-16 phone test). An older marker without a pid follows the time rule.
  - *Half-written files.* The library is written to `dmsh_vk.lib.tmp`, flushed and renamed (`vk_android_build.py write_library`); a `.tmp` a stopped build left (and a result file never renamed, `results/*.tmp`) is removed at the next start when no build's marker is fresh (`LayerDir.tidy`). `built.tsv` and `layer_state.json` are written by rename. A request pair that does not hash to its name (a control file cut short, a code file gone) is a problem: once it is older than a minute its files are removed, so the host writes it again when the game next asks for the program (younger ones may be being written and wait). A cut last line of `pairs.tsv` has no key among the requests and is skipped.
  - *Failures.* `built.tsv` rows are `key`, `ok` or `fail`, and the tools version (`DMSH_VK_CHAIN`) that built them. A failure settles its request for that version only: an APK with another chain version (a translator fix) has its own list and tries it once more, not every run (`LayerPending.pending(root, version)`, `shader_layer.py settled`).
  - *One tool at a time in `:pack`.* Prepare (`PackService`) and the layer build (`LayerService`) run their tools in one embedded Python, which `shader_layer.py run_build` changes (`os.environ`, `sys.argv`) as the services' `PackEngine.setenv` do. One lock, `PackLock` (a static both services use), decides: a layer build starts only when nothing holds it (`tryLayer`: no job exists, no other build runs); a job holds it from its start or resume to its end, so no build starts between its steps; a job that starts while a build runs asks it to stop (`PackEngine.interrupt` every 2 s until it has, and the service checks `layerStopAsked` before its tool starts: the translation stops after the shader in hand, its result files stay, and the next build carries them, below) and waits, the card saying "Waiting for the shader build to end" (`PackService.waitForLayer`; a Pause meanwhile pauses the job).
  - *Heat and battery* (`LayerGuard.pace`). The watcher and the service read `PowerManager.getCurrentThermalStatus()`, `getThermalHeadroom(10)` (asked every 10 s at most) and `BatteryManager`. **Heat never stops the build; it only reduces it to one worker** (and a note on the label). Status 2 (moderate, which the game alone reaches after about 2 minutes): every worker (up to 3) while many requests wait (`MANY_PENDING`, 150) and the headroom is under 0.85 (`HEADROOM_WARM`), else one; label note "phone is warm"; a headroom at or over 1.0 (`HEADROOM_HOT`) takes it to one worker with the note "phone is hot: 1 worker". Status 3 and above (severe, critical, emergency, shutdown), a game in front or not: one worker and the same hot note (`procs` returns 1 from status 3). The sampled check obeys the same rule: heat never holds it. Only a battery under 15 % that is not charging (and a full layer folder) waits, and says so ("Shader build paused (battery low)"). At critical status Android itself may close the app; the next start goes on from `built.tsv`. The label's choice (Off, Number only, Full text) is only what is drawn: `LayerStatus.buildDue` has no label argument, and a screen that throws while drawing it cannot take the tick with it. Nothing of this reaches the host. The phone must show: a status-4 phone keeps building with one worker and the hot note.
  - *First start.* The first start of a game that has no library shows once (per game, `Prefs.layerExplained`) what to expect: pop-in for a while, the label, Prepare shaders, a library from a computer.
- **Build order and cost.** A run takes the requests in the order the game asked for them (the `.ctl` files' times), a program's stages together (`pairs.tsv`), at most a batch of new ones: `max(64, half of those already built)` (`--batch`), so the first library comes after one small batch and later runs grow with the layer; the requests already built are in every run, as the library is written from all of them. Workers: `DMSH_VK_PROCS` and `DMSH_VK_XLATE_J` are 2 on a phone with 6 or more cores that is not warm, else 1 (`LayerGuard.procs`); with 150 or more requests waiting and the phone under status 2, half the cores, 2 to 3. Measured 2026-11-16 (OoT castle, no library, system driver): 1 worker 0.1-0.3 s per new shader (runs of 2 to 222 shaders took 3 to 45 s, back to back), 3 workers only 1.15x; `top` showed 14.8 of 15 GB used, 4.6 GB swapped, `kswapd0` at 76 % CPU: the phone is memory-starved with the game running, so more workers do not help until memory pressure drops. **Where the time goes** is logged once per run: `shader_layer.py` prints `shader_layer timing: N shaders in T s, R/s (cpu U+S s): setup …, translate … (cpu …), library …, check …, after …; peak … MB; free A to B MB, swap C to D MB` (`PhaseClock`, from the build's own progress lines; no chain file is touched) and `LayerService` repeats it in logcat (tag `nxlayer`). A translate CPU time far under its wall time means the run waits for memory or storage, not for the translator. Plan if that confirms it (not started): keep one long-lived interpreter and tables warm in the service, append layer segments instead of rewriting the whole library each run, skip the spirv-val pass for layer shaders (the full build validates the same module); each only with a test that the libraries stay byte-identical. A native in-process port of `finish()` is the large option and waits for these numbers.
  The layer's temporary profile tables (`shader_map.tsv`, `shader_pairs.tsv`) change with every new request, and with them the profile's inputs digest that every result file is stamped with (`dmsh_chain.inputs`): each run translated every request again. `carry_results` moves the last run's result files to the new digest (the 12 hex digits rewritten in place in the JSON head, so a stop leaves a stale result, never a wrong one) when the game's own inputs are the ones recorded in `lib/v-<V>/layer_state.json` and, for a vertex shader, its paired pixel shaders among the layer's keys are the same (its padding depends on them; otherwise it is translated again). The state is saved as a run starts, after its carry (`save_state`): every result the run writes has its digest and, for a vertex shader, its pairs, so a run that was killed half way (lmkd, or a Prepare that stopped it) leaves results the next run carries as well as one that ended; a result whose head has any other digest is never moved (tests: `test_killed_run_is_carried`). No chain file changed.
  Measured on the Mac (DKB, `040074A01BF12000`, 2026-11-16, `J=8`, requests extracted from the shader package in the game's work folder): 2,000 requests from nothing 36.9 s; a run with no new request (all results there) 1.4 s, so re-reading the results and rewriting the 17.7 MB library is cheap; 20 more requests before the carry-over 37.6 s (every shader translated again), with it 2.4 s (16 translated, 2,037 carried), and that library is byte-identical to a fresh build of the same 2,053 requests. 300 requests in batches: three runs of 64 new shaders, 2.7-2.9 s each. Not measured on a phone.
- **Seeding a first start.** `python3 dm/gfx/tools/shader_seed.py --game <id> --root <layer folder> --first <shader_first.tsv> --romfs <spec> [--main <spec>] [--limit N] [--dry-run] [--jobs J]` writes the requests of a starter list (rows `key`, `stage`, most wanted first) before the game asks: it reads each key's record from the RomFS file the profile's `shader_map.tsv` names, with `shader_split.py`'s own readers (`scan_jobs`, `scan_file`; only those files, `--romfs` as `shader_split.py` takes it, a picked `.nup` through `DM_NUP_FD`), and writes `req/<key>.code`, then `req/<key>.ctl` renamed into place (the control cut to the host's 0xd8 bytes), only when the bytes hash to the key, and appends the profile's pairs of two requested keys to `req/pairs.tsv`. The `.ctl` times run in the list's order, five minutes in the past, so the build takes the list in its order and every request the game writes is younger. A key already requested is left; a key whose source is main's or a captured file, or that the dump lacks, is counted and left (exit 0); SIGINT stops it with every written request whole (exit 130). Tests: `dm/tools/tests/test_shader_seed.py`. No chain file is touched. Measured on the Mac (Ocarina of Time `0400486024DEC000`, the `.nup`, 20 keys in 14 files): 10 s with 2 workers. Not run on a phone.
- **Open:** none of this has run on a phone (the quota, the marker's beat, `PackLock` and the per-version lists included: JVM and Mac tests only). The no-library start and `DM_VK_LAYER_DIR` were compiled with the NDK (`libnxhost.so`) and their pure parts tested on the Mac (`t_android_layerreq`); the launcher side (`LayerDir`, Play without a library, code-only Prepare) is tested on the JVM only. Unmeasured: the build's time on the phone while a game runs, its effect on frame pacing and heat, whether `:pack` stays alive under battery and RAM-saver limits, how a game behaves with compute shaders missing at first. The vertex shader of a program with a missing pixel shader is rebuilt in the layer (the requests carry every stage and the pairs); not checked on a phone. A Maxwell (non-NVN2) control section is not copied, so those games get the list but no layer. The safeguards (switch, quota, heat and battery, first-start message) and the first-hit build order are tested on the JVM and on the Mac only. The layer's lifetime rules, the request writer's retries and the pipeline-cache stamp (host) are tested on the Mac and linked with the NDK only; the heap the copies take in a long no-library run is not measured.

### A shader order without playing

`python3 dm/tools/shader_priority.py <title ID> [--top N] [--no-sibling] [--eval]` ranks a game's `shader_map.tsv` from the profile's static tables alone and writes `dm/games/<id>/shader_priority.tsv` (`key`, `stage`, `score`, `reason`; the first 20,000 rows; generated, git ignores it; deterministic; the score orders and is not a probability). `--eval` measures the order against the game's own `shader_seen.tsv`. What the tables offer: `shader_pairs.tsv` and `pso_pairs.tsv` carry nothing (every vertex shader of the three games is paired with the same one or two pixel shaders), `shader_facts.tsv` only the thread group of compute shaders, `shader_map.tsv` one source per key (where it first appears, so "repeated in many files" is not recorded). What is usable: the source (a shader inside the executable or a loose file against the bulk archive), the stage, the container as a unit (play asks for a whole shader-archive resource or none of it; a container shape that occurs once is likelier than one repeated per material), code sizes from the `GLSLC@` offsets, and, as an option, a sibling profile (a container of the same shape in another game of the engine and what share of it that game's play asked for; the game's own `shader_seen.tsv` is never read). Tests: `dm/tools/tests/test_shader_priority.py`.

Measured on 2026-11-16 (share of the real `shader_seen.tsv` found in the top N; random order would give N / map size, 1% at 1,000 up to 15% at 20,000):

| Game (map, seen) | Top 1,000 | Top 2,000 | Top 5,000 | Top 10,000 | Top 20,000 |
|---|---|---|---|---|---|
| Pokopia `0400A3A01EE4C000` (131,426; 8,174), static only | 9.1% | 17.1% | 53.7% | 61.3% | 68.9% |
| Pokopia, with sibling prior | 3.7% | 3.7% | 31.5% | 73.3% | 79.8% |
| Hyrule Warriors `04003F40232DE000` (101,860; 15,449), static only | 2.9% | 3.8% | 8.1% | 9.4% | 9.4% |
| Hyrule Warriors, with sibling prior | 5.0% | 7.8% | 12.0% | 15.7% | 15.7% |
| Yoshi `0400245021D2C000` (133,154; 1,519), either | 0% | 0% | 0% | 14.7% | 24.3% |

Verdict: the order is not good enough to stand in for play. It lifts over random order only where a game keeps what it needs outside the bulk archive (Pokopia: the executable's and loose files' roughly 700 shaders are 92-100% asked for, and one small resource holds 4,238 more; there the first 5,000 keys reach 54% of what play asks for at 88% precision). In Hyrule Warriors play asks for 15% of the map, in large containers whose shape says nothing, so 20,000 keys reach 9-16%; in Yoshi (Unreal Engine, assets by path) the static signals found nothing in the first 5,000. The seen sets are whole containers, and which container is common is a fact of the game's rendering, not of its tables. The sibling prior helps a game of an engine that another profile has been played in (Hyrule Warriors 8% to 12% at 5,000) and can hurt (Pokopia 54% to 32% at 5,000), so it is a seed for a game with no list at all, not for one with a list. The weights are hand-set from these three games, not fitted per game; three games cannot say how they carry to a fourth.

- (a) The on-demand layer: usable as the order of a background queue (keys the layer has not been asked for yet, built while the phone charges), never as a reason to build before play: precision at 5,000 is 18-88%, and a key built that play never asks for costs the same minutes as one it does. The layer's own requests stay first. A seed set for a partial Mac library: only for a game with an executable or loose-file group (Pokopia's first 5,000 keys are a 54% start; the rest comes from `scripts/shader_harvest.py`).
- (b) Not worth it as the source of a `shader_seen.tsv`: play and harvested `[shaders-missing]` lines stay that.

### Prepare without shaders

A game the layer covers (`ShaderLibs.layerCovers`: title ID `0400…`, `DM_VK_LAYER` not switched off) is prepared with no shader translation by default: `Job.codeOnly` (job.json `code_only`) runs identify, rewrite and pack, finishes "done" and the game plays at once, the layer building the shaders it asks for. The pack has no `shaders/v-<V>/dmsh_vk.lib` and no `shaders` row in `pack.tsv`, which is valid: `Pack.read`, `PackZip` (Import pack… / a `.nup` pack zip) and the host do not need one. Its pack step runs `pack_android.py --optional-shaders` (a current library in the cache is copied, else none is made). The translation of the whole set is the optional job the player starts later (**Prepare shaders**, dialog: "The game plays now and builds shaders while you play; this builds the whole set now (about N minutes)"), or in the same go with "Also build all shaders now" in Prepare's dialog; a game the layer does not cover keeps the whole Prepare. On a computer `scripts/pack_android.py --no-shaders` makes the same pack, and a pack made with a full library moves to the phone as before.

That later job reuses what the layer built: `DMSH_VK_DELTA_FROM` is the pack's `shaders/` and `shaders/layer/lib` (`v-<V>/dmsh_vk.lib` of the run-time layer). The delta's rule is unchanged: an entry is taken only when its hash is the profile's manifest hash for the key, so only an entry equal to the full build's is kept. A layer vertex entry is padded for request-only pairs and so usually differs from the full build's: it is translated again, never taken on trust; with no manifest of this version, or no row for a key, nothing is reused. Tests: `dm/tools/tests/test_android_prepare_code_only.py`. Not run on a phone.

### Optional shaders

The rule: building shaders is always the player's choice while the game can play without them, and the launcher recommends it where it helps; it is required only when nothing plays (no library the host plays and a game the shader layer does not cover). `ShaderState.need(covered, olderPlays, code, shaders)` decides Prepare for a pack that is there (`Ondevice.checked`): `covered` is `Pack.shadersOnDemand` (no library, the layer builds them all), `olderPlays` an older library the host plays (`Pack.playableLibrary`, `Pack.legacyLibrary`; the layer fills what it lacks when it covers the game). A code update never needs new shaders (they depend on the profile's shader inputs, not on the code), so with either one it rewrites the code only and keeps the pack's library (`CODE_SHADERS_OPTIONAL`: the code-only pack step, `--optional-shaders`, leaves the other `v-<V>` folders alone): the dialog says "Recommended: build all shaders now for smoother play (about N minutes, best on the charger). You can play now; …" (`PrepareText.recommendText`) and keeps the box **Also build all shaders now** (ticked when the player came from Update shaders or Build all: `Ondevice.prepareShaders`); an automatic code update (`autoCodeUpdate`) or a start from adb takes the code only. A shaders-only Prepare of a pack that plays is the same offer (`SHADERS_OPTIONAL`). A library of this APK's version made from other shader tables does not count as playable (the host would load it and draw some shaders wrong), nor does a game the layer does not cover with no older library: Prepare then makes the shaders as before (`CODE_AND_SHADERS`, `SHADERS`), and an automatic update never starts that whole job.

Found 2026-11-21 on Fire Emblem: Fortune's Weave (`04007EF01F8AE000`): a pack made on a Mac with `v-19662e4c4a25` and `v-6257cc4482ac`, an APK of `6eaa66f9f1e4` whose profile manifest was of `65883461079b`, and a code update (its `patches.py` changed): Prepare offered only the whole job, "delta: none … a full build", 16,888 shaders. The old rule took the code-only path only for `layerCovers && libraryOf == null` and treated an older playable library as needing the whole set.

The other places follow the same rule: a delta update starts by itself only when nothing plays meanwhile or it is small (`ShaderLibs.autoDelta`, above); an automatic update never resumes a job the player paused; a job stopped in its shader translation can **Finish without shaders** (`ShaderState.canSkipShaders`) when the game plays without the set and the job makes the code (`Job.redoesCode`, job.json `redo_code`) or the pack does not play yet; the card's "Shaders needed" stays only for a pack nothing plays (`GameSettings.shadersNeeded`). Tests: `dm/tools/tests/test_android_shader_state.py` (`test_need`, `test_auto_delta`, `test_skip_shaders`, the wiring). Not run on a phone yet.

### Launcher states for shaders

What the launcher shows and does for each combination, so that no state leaves the player without a way forward (`MainActivity.problem` / `check` / `launch`, `GameSettings.shaderUpdateCard`, `Ondevice`; the words are `ShaderState`, tests `dm/tools/tests/test_android_shader_state.py`). *Covered*: a Switch 2 title (`0400…`), Game settings › **Shaders while playing** on (`Prefs.layerBuild`), no `DM_VK_LAYER=0` among the game's own lines (Extra environment), and a folder the layer can be built in: the pack's `shaders/layer`, else `files/temp/<id>/shader_layer` (`ShaderLibs.layerWritable`; with neither the host has no layer and an empty library draws nothing, so such a game is not treated as on demand). *Dump*: a game file Prepare can start from (`Pack.isDump`: a dump folder, a `.nup`, also one picked in place); any other file (a game added with a pack only) cannot be prepared on the phone. The pack source (the app's `packs/<id>`, a picked pack folder, one beside the dump) changes nothing but whether its `shaders/layer` can be written.

Prepare jobs over those states: a new Prepare of a covered game is code-only (`Job.codeOnly`): when it is done the job's card goes (`Ondevice.Panel.ready` takes a code-only job without a library) and the game's card says "Ready" at once. While a **Build all** (Prepare shaders of a code-only pack) or an update runs, waits or has failed, its progress card stands where the game's card was and its Play stays on whenever the pack plays as it is (an older library, one from before the ABI field, or the layer: `Ondevice.Panel.playsOld`, `playsOnLayer`); a failed Build all leaves the code-only pack playable. Build all goes through Prepare's check of the dump: a dump that is gone shows "Game file gone" with Pick it again on the card, one that cannot be prepared any more says why ("Cannot prepare this dump"). The page's rows show for a `.nup` picked in place too (its stand-in path has no file: `PickedNup`).

**Import a library** (`PackUi.importLibraryPick`): the system file picker for one `dmsh_vk.lib`, read through its document (no path needed), copied by a worker thread to `<pack>/shaders/.import-dmsh_vk.lib.tmp`, checked (`ShaderLibs.importProblem`: a library this app reads, of this game, of this APK's ABI or one of `DMSH_VK_ABI_COMPAT`, a 12-hex-digit version in its header, entries and blob inside the file, and for this APK's own version the profile's inputs; one made before the ABI field is refused), then `inputs.tsv` (from its header) and the library are renamed into `shaders/v-<its vk_chain>/`. Refused while the game runs or an export or import of its pack works; a refusal says why and changes nothing. The page is built again after.

**Settings › Storage** while a game runs: refused ("A game is running"), as before, so "Shader cache built while playing" is never deleted under a running game; the `:pack` process that also hosts the layer's build refuses only while it runs something (Android keeps it cached after a game: that no longer blocks Storage). A deleted layer is made again at the next start (`LayerDir.resolve`).

Open: none of this has run on a phone; the decisions and words are tested on the JVM, the screens were only compiled.

### Targeted split

The phone's split (`PackService`, and `pack_android.py`'s) runs `shader_split.py` with `DM_SPLIT_TARGETED=1`: when the dump's main build is one of the profile's `build` rows and the profile has a `shader_map.tsv`, it reads only the RomFS files that hold the profile's shaders instead of every file. Those are the files the map's source column names (a member's source, such as `/Lib/agl/agl_resource.sarc.zs/agl_technique_pfx.sharcb#BAHS@…`, is reduced to its RomFS file, here `Lib/agl/agl_resource.sarc.zs`) and the files of the profile's `shader_files.tsv`, when it has one. The map names only where each key first appears. A file that holds only copies of shaders found earlier can still pair them in a new way (Donkey Kong Bananza: 42 of its 15,576 pairs). `shader_files.tsv` lists every file a full split found any shader in: run a full split with `DM_SPLIT_FILES=dm/games/<id>/shader_files.tsv`. The files keep the full scan's order, so the first appearances are the same. The result is kept only when its tables (`shader_map.tsv`, `shader_facts.tsv`, `shader_pairs.tsv`, `pso_pairs.tsv`, each the profile has) are the profile's byte for byte. Otherwise every file is scanned, with a `targeted split: not taken, <why>` line in `split.log`. The reasons are another build (Try anyway, a newer update), a file the map names that the dump lacks, a Unity serialized file that needs a borrowed type tree, or tables that differ. The outputs are the full scan's either way. With `DM_SPLIT_RESUME` the two scans keep their results apart (`<dir>/targeted`, `<dir>/full`). A targeted scan that differed is not tried again on the same inputs (`<dir>/targeted.failed`), so a stopped fall back resumes as the full scan. Neither `shader_split.py` nor `shader_files.tsv` is part of `DMSH_CHAIN`, `DMSH_VK_CHAIN` or the profile's input digest: no library version moves. The card's count is of files: "Finding the shaders: 1,203 of 1,890 files" (`PrepareText.stepCountText`). Measurements: [Prepare reads every RomFS file to find the shaders](../docs/reference/packing.md#prepare-reads-every-romfs-file-to-find-the-shaders).

### Translator answers

The translator asks the host a few questions whose Apple answers are wrong on the phone. `vk_android_build.py` puts the phone's answers into every job (`ANSWERS`), as job keys `Program.cs` reads; the Apple jobs (`dmsh_build.py`) carry none of them, so `Program.cs` gives Ryujinx's defaults there and the Apple translations stay byte-identical (checked on 387 DKB keys of every stage: the `.spv` and `.res.json` of the translator before and after the change are the same bytes). `DMSH_CHAIN` moved with `Program.cs` (`725d300e1fae`), so the Apple libraries have a new version with the same contents.

| Job key | Ryujinx query | Apple (unset) | Android | Effect |
|---|---|---|---|---|
| `subgroup_size` | `QueryHostSubgroupSize` | 32 | 64 (`DMSH_VK_SUBGROUP_SIZE`) | Maxwell code assumes 32-lane warps. With 64, ballots read the 32-bit half of the lane (`laneId & 32`), the lane masks likewise, votes go through ballots, shuffles stay inside the lane's 32-lane segment (`InstEmitWarp.cs`, `HelperFunctionManager`). Right on 32- and 64-lane devices |
| `ssbo_align` | `QueryHasUnalignedStorageBuffer`, `QueryHostStorageBufferOffsetAlignment` | false, 16 | true, 64 (`DMSH_VK_SSBO_ALIGN`) | every access computes its offset from the base address rounded down to 64 (`GlobalToStorage`): the replay binds `SBUF`, `SBUF_UBO` and `UBO_PTR` buffers at `addr & ~63` with the range grown by `addr & 63` |
| `gs_passthrough` | `QueryHostSupportsGeometryShaderPassthrough` | true (false only in Metal's compute lowering) | false | a passthrough geometry shader writes its vertices itself (`EmitterContext`); no `SPV_NV_geometry_shader_passthrough` |
| `shared_max` | `QueryHostComputeSharedMemoryMax` | 0 (no limit) | 32768 (`DMSH_VK_SHARED_MAX`) | a compute program whose shared memory (with the HMMA scratch) is over it keeps its shared memory in a storage buffer, a slice per workgroup (`SHARED_SPILL`, [Compute programs over the device's shared memory](../docs/reference/shaders.md#compute-programs-over-the-devices-shared-memory)); the entry's `shared` is then what stays in workgroup memory |
| `gather_bias` | `QueryHostGatherBiasPrecision` | 0 | 8 (`vk_android_build.py` `GATHER_BIAS`, a constant of the target, never a probe of the building machine) | each gather coordinate moves 1 / (size × 512) texel (Ryujinx `TexturePass`): Adreno's texture unit, under Qualcomm's driver and Turnip alike, otherwise takes the footprint before a texel edge that Maxwell passes (dark tile boxes, Eden #4565). Half of one 8-bit sub-texel step, so on GPUs that already agree with Maxwell (Mali) only coordinates within that half step below an edge move, to Maxwell's footprint |
| `ssbo_align` (also) | `QueryHasConstantBufferDrawParameters` | false | true | c0 + 0x644 in a vertex shader reads the `BaseInstance` builtin, which holds an indirect draw's base instance (PR #83; base vertex and draw index stay in c0) |

The emulated passthrough keeps NVN's viewport mask for one use: it drops a primitive whose mask is 0 (the culling geometry shaders of DKB's terrain do this). Adreno has no `SPV_NV_viewport_array2`, so the build turns the `ViewportMaskNV` output into a `Private` variable (`private_viewport_mask`, entry flag `F_VIEWPORT_CULL`): the cull stays, the routing of a primitive to the viewports its mask names is lost (no difference in a single-viewport draw). The library header records `subgroup_size` and `ssbo_align`; a library made before them has 0 in both (32 lanes, exact binding).

A note for the Apple side, not changed here: Ryujinx's multi-target storage path (`TryGenerateMultiTargetStorageOp`, an address traced to several possible buffers) always rounds the base down to the alignment answer (16), while the inline path does so only when `QueryHasUnalignedStorageBuffer` is true, and `nvn_mtl.m` binds at the exact address. A multi-target access to a storage buffer whose address is not 16-aligned reads 1–15 bytes off on Metal. The Android answers make both paths round to 64.

### Variants

A pixel shader's entry can hold several modules (`dmsh_vk_module.variant`, base first); the replay picks one by the pipeline's state:

| Variant | Which shaders | Module | Pick it when |
|---|---|---|---|
| `MOD_BASE` 0 | all | as translated | otherwise |
| `MOD_UINT` 1 | `F_INT_OUT` (an output written from integer bits) or a shader that writes only constants (a clear into an integer target): `fs_uint`'s rule | every float colour output retyped to the `uint` vector of its bits (`OpBitcast` at each store, back at each load) | every colour attachment is a `UINT` format |
| `MOD_UINT_MIXED` 2 | the above when it also writes float outputs | only the outputs written from integer bits retyped; entry byte `uint_mask` names them | the `UINT` attachments are exactly `uint_mask` |
| `MOD_DUAL` 3 | the profile's `dual_want.tsv` shaders that write exactly colours 0 and 1 (`fs_dual`; DKB has no table, so none) | output 1 at `Location 0, Index 1` | target 0 blends with a `SRC1` factor (`dualSrcBlend`) |

A pipeline with `SINT` attachments has no variant yet (neither has Metal). The alpha test is not a variant: every pixel shader whose colour 0 is a float `vec4` carries a uint specialization constant `SpecId 1` (`DMSH_VK_SPEC_ALPHA_FUNC`, entry flag `F_ALPHA_TEST`, in every variant): `NVN_ALPHA_FUNC_*` (1 never … 7 gequal, 8 always), default 0 = no test, which the driver folds away. The comparison of colour 0's alpha with the reference runs before every return and discards on failure. The reference is per draw: the float bits of word 0 of the fragment stage's `SUPPORT` buffer (Ryujinx's `alpha_test` field, which no translated shader reads), so a reference that changes every draw keeps the pipeline, as `dmsh_alpha.py` does on Metal with its buffer.

## Descriptor ABI

`dm/gfx/nvn/dmsh_abi_vk.h` holds the numbers; `dm/gfx/nvn/dmsh_abi.h` still defines the driver segments (`c0`, `c2` tables) and what each kind means. Every pipeline has the same layout shape:

| Set | Binding | Holds |
|---|---|---|
| 0 | stage × 64 + n | the per-draw resources of each stage: n in the translator's order. Stages numbered as NVN does: vertex 0, tess control 1, tess evaluation 2, geometry 3, fragment 4. A compute pipeline uses range 0 |
| 1 | 0 | `SAMPLED_IMAGE[2^20]`: the NVN texture pool by texture ID. Update-after-bind, partially bound |
| 1 | 1 | `SAMPLER[4096]`: the NVN sampler pool by sampler ID |
| 2 | 0 | `STORAGE_BUFFER`, 128 KiB, a set of its own (Qualcomm's driver never wrote it as set 1 binding 3), bound with set 1 when pool reads are reported: the bitmap of the texture IDs shaders read through the texture pool. Not in the library: the replay adds the code that writes it to every module it makes (`vka_spvpatch.c vka_spv_pool_fb`; [Textures read only through the pool](../docs/reference/rendering.md#textures-read-only-through-the-pool-were-never-made-android)) |

No push constants: NVN2's pushed constants (`c[24]`, 256 bytes) are a uniform buffer like the driver segments.

Each shader's binding records (`dmsh_vk_bind`) give the kind, the Vulkan descriptor type, the binding and count, and the NVN slot to fill it from:

| Kind | Descriptor | Fill from |
|---|---|---|
| `CBUF` reg | `UNIFORM_BUFFER` | uniform slot reg (`c[3 + reg]`): the bound address and size. Declared as `vec4[4096]`: bind the game's size, at most 64 KiB |
| `C1` | `UNIFORM_BUFFER` | the entry's c1 bytes (`c1_off` / `c1_len` in the blob), a static buffer per shader |
| `DRVCB` reg 0 / 2 | `UNIFORM_BUFFER` | a `DMSH_DRV_SIZE` buffer filled as `nvn_mtl.m` fills `NVN_RB_DRV0` / `DRV2`: the stage's storage buffer table, the c2 handle tables, the words of `dmsh_abi.h` (dispatch size, point size 2047, sample table, base instance). `index.json` `drv_reads` lists the offsets each shader reads |
| `DRVCB` reg 24 | `UNIFORM_BUFFER` | the stage group's `DMSH_PUSH_SIZE` pushed bytes (`NVN_RB_PUSH`) |
| `SUPPORT` | `UNIFORM_BUFFER` | Ryujinx's support buffer: zeros, then `render_scale` floats at 192 + 16 i set to 1.0 (`support_buf` in `nvn_mtl.m`); in the fragment stage word 0 holds the alpha test reference (float bits) |
| `SBUF` reg | `STORAGE_BUFFER` | storage slot reg: address and size from the stage's `c0` table, bound at the address rounded down to the header's `ssbo_align` (64), the range grown by the difference. Flag `RW` when written |
| `SBUF_UBO` reg, off | `STORAGE_BUFFER` | the address the game keeps in uniform slot reg at byte off, bound as `SBUF` |
| `UBO_PTR` reg | `STORAGE_BUFFER` | compute uniform slot reg, through its `c0` entry (`DMSH_C0_CS_UBO`), bound as `SBUF` |
| `TEX` reg + `skind` | `COMBINED_IMAGE_SAMPLER` (or `SAMPLED_IMAGE`) | the texture ID of slot reg's handle (combined slots `0x20 + 8 r`, separate textures 128 + r) and the sampler the sampler half names: `SAMP_TEX` the same handle's sampler ID, `SAMP` separate sampler slot sreg, `SAMP_ID` the constant sampler ID sreg, `SAMP_UBO` the handle in uniform slot sreg at byte soff |
| `TEX_UBO` reg, off | `COMBINED_IMAGE_SAMPLER` | the 32-bit handle in uniform slot reg at byte off (low 20 bits texture ID, high 12 sampler ID), sampler as above |
| `TBUF` reg | `UNIFORM_TEXEL_BUFFER` | the buffer texture in slot reg. Flag `FETCH1D` on a `TEX`: a 1D integer fetch the translator made a 2D read of 16384-texel rows (`tbuf_as_2d`) |
| `IMG` reg | `STORAGE_IMAGE` / `STORAGE_TEXEL_BUFFER` | image slot reg (`c2 0x120 + 8 r`). Flags `RW`, `ATOMIC` (R32Uint / R32Sint only) |
| `IMG_UBO` reg, off | `STORAGE_IMAGE` / `STORAGE_TEXEL_BUFFER` | the 32-bit image handle the game keeps in uniform slot reg at byte off (low 20 bits the texture ID, with the pool base as `TEX_UBO`'s), bound as `IMG`; Unreal Engine 5 on the Switch 2 keeps its images there ([Images whose handle is in the game's uniform buffer](../docs/reference/shaders.md#images-whose-handle-is-in-the-games-uniform-buffer)) |
| `TEX_C2A` / `SAMP_C2A` off | arrays, count elements | element k from the c2 handle at byte off + 8 k; `soff` a sampler word ORed into every element |
| `TEX_POOL` / `SAMP_POOL` | set 1 | nothing per draw: the pools |
| `GMEM_MAP` | `STORAGE_BUFFER` | the pool table for raw global memory (`DMSH_GMEM_MAP_*`), delta = buffer device address − guest address: the shader goes through `PhysicalStorageBuffer` pointers, so the device needs `bufferDeviceAddress` |
| `GMEM_LOG` | `STORAGE_BUFFER` | the write log of those stores, cleared per draw or dispatch |
| `SHARED_SPILL` | `STORAGE_BUFFER` | a compute program's shared memory past `shared_max`: the record's `bytes` per workgroup slice, slices for the dispatch's workgroups (or as many as the replay's spill buffer holds, the dispatch then made in parts) |
| `UNKNOWN` | | the replay refuses the shader (none on DKB) |

`dim` gives the image shape (SPIR-V `Dim`, array, multisample, depth compare, sampled type) for a null or placeholder descriptor of the right type. The aliased pool binding wants the descriptor at texture ID i to be a view of the type every shader samples it with; the same ID read as two view types needs a second set of views (none seen yet: DKB reads no pool).

### Depth and Y

- **Depth.** The game sets NVN's depth mode at run time. Modules that write a position (vertex, tess evaluation, geometry) carry the bool specialization constant `SpecId 0` (`DMSH_VK_SPEC_GL_DEPTH`, entry flag `F_GL_DEPTH`): false leaves z as translated (near = 0), true writes z' = fma(z, 0.5, w × 0.5) (near = −w, NVN's default), the arithmetic of the Apple `main0` entry point. Set it on the last pre-raster stage only (a vertex shader that feeds a geometry shader keeps false), or keep false everywhere and use `VK_EXT_depth_clip_control` with `negativeOneToOne` where the device has it.
- **Y.** The translator writes clip space for Metal: y up, window origin upper-left (`QueryGraphicsState`). Vulkan's y points down, so the replay sets each NVN viewport with a negative height (y + h, −h), which every Vulkan 1.1 device takes; `FragCoord` stays upper-left as on Metal.

### Stage interface

- Vertex inputs: `Location` = NVN attribute index, all `vec4`; `vin_mask` / `vin_types` (2 bits a location: float, sint, uint) give the class the vertex input format must have (`VK_EXT_vertex_input_dynamic_state` takes the formats per draw). A float input fed a `UINT` / `SINT` format (DKB: RGBA8UI, RG8UI, R8UI, RG32UI) keeps that format, and the pipeline's vertex module is the base one rewritten (`vka_spv_vin_retype`, keyed by the locations in `vka_gkey.vin_u` / `vin_s`): the input becomes a `uvec4` / `ivec4` and every load of it (or of a component through an access chain) is bit-cast back to float, so the shader sees the integer bits Maxwell's fetch puts in the register. A USCALED stand-in gave the bits of the converted float (5 → `0x40a00000`). `t_android_spvpatch` checks the rewrite with spirv-val (`DM_VK_SPV_DIR=<folder of .spv>`: 400 DKB vertex modules, all rewritten and valid). 32-bit `*_I2F` formats into float inputs still bind a `UINT` format (logged).
- Colour outputs: `Location` = render target; `fout_mask` / `fout_types` (the base module's). `F_INT_OUT`: an output written from integer bits through a float output, which an integer attachment does not take: take the `MOD_UINT` or `MOD_UINT_MIXED` module ([Variants](#variants)).
- Compute: the workgroup size is in the module (`LocalSize`) and in `local`; shared memory is declared in the module, except a `SHARED_SPILL` program's, which is in its storage buffer.
- Entry point `main` in every module; `F_EARLY_Z` modules have `EarlyFragmentTests`.

| Part | Size | |
|---|---|---|
| `dmsh_vk_header` | 128 | magic `MSVK`, version 1, `chain`, `vk_chain`, `game`, `inputs` (16 bytes each, NUL padded), then counts and offsets of the three tables and the blob, `subgroup_size` and `ssbo_align` (the translator answers; 0 in older libraries), `abi` (12 hex digits, `DMSH_VK_ABI`; zero before `ea193cf243cd`) |
| `dmsh_vk_entry` × n | 64 each | sorted by `key` (the 16-hex shader key as a big-endian number): binary search with the host's program key. Stage, flags, first module and count, first binding and count, compute size, c1 bytes (offset: `c1_off`, high 32 bits in `c1_off_hi`), vertex input and colour output types, `uint_mask` (the `MOD_UINT_MIXED` module's integer targets) |
| `dmsh_vk_bind` | 24 each | the records above |
| `dmsh_vk_module` | 16 each | offset in the blob (`off`, bits 32-47 in `off_hi`), SPIR-V size, stored size, variant (`MOD_*`, the base first), codec: `RAW` or `ZSTD` (one frame; the replay links zstd's decompressor) |
| blob | | from `blob_off`, 16-byte aligned pieces: the modules and the c1 bytes |

The format stays version 1: the header and entry fields above came out of reserved bytes (zero in an older library, which means 32 lanes, exact storage buffer binding, no mixed module, offsets under 4 GiB), and an older library's entries have only the base module. A new variant is another module record of the same entry, with the next `DMSH_VK_MOD_*` number.

**Libraries past 4 GiB.** Pokémon Pokopia's 131,426 shaders make a blob of about 9.8 GB, past what 32-bit offsets address. A module's offset takes bits 32-47 from `off_hi` and an entry's c1 offset its high 32 bits from `c1_off_hi` (`vka_shlib_mod_off`, `vka_shlib_c1_off`; `vk_android_delta.py` `mod_off`, `c1_off`); both are 0 in a smaller library, which is written as before. `c1_off_hi` is a position in the file, so the [entry hash](#delta-updates) leaves it out as it leaves out `c1_off`. `write_library` keeps only the tables in memory and copies each module from its result file into place (`Stored`), and `--check` maps the library instead of reading it: neither holds the blob in memory as a whole.

## What the replay does

In `dm/gfx/vk_android` (branch `android-draws`): `vka_shlib.c` (reader), `vka_bind.c` (binding walker), `vka_shader.c` (library, modules, programs), `vka_pso.c` (layouts, pipelines, pipeline cache), `vka_draw.c` (draw state, render pass, descriptors, draws and dispatches). [PORTING.md](PORTING.md#the-nvn--vulkan-replay) has the replay as a whole.

1. **Library.** At the first program a draw resolves, map `<pack folder>/shaders/v-<DMSH_VK_CHAIN>/dmsh_vk.lib` (the folder the modules came from; `DM_VK_SHLIB=<file>` overrides). When it is missing (the app's delta update is making it), the newest other `shaders/v-<V>/dmsh_vk.lib` of the game whose header `abi` is the host's `DMSH_VK_ABI` is mapped instead, with a log line naming both versions (`vka_shader.c lib_load`, `vka_shlib_check`'s `abi`); failing that, the newest one of the game made before the `abi` field, with a `[RED]` warning; a capture records the library actually loaded. Refused with one `[RED] vk: shader library … refused: …` line unless `magic`, `version`, `chain`, `vk_chain` (or, for that older library, `abi`) and `game` (the profile's `DM_GAME_ID`) match, or when the device's `minStorageBufferOffsetAlignment` does not divide the header's `ssbo_align`; every table and range is checked once at open. A device whose subgroups are not 32 or 64 lanes (for `subgroup_size` 64), or vary, is logged. Without a library the game runs on and draws nothing.
2. **Programs.** A program (by its serial, which `nvnProgramSetShaders` renews) resolves each stage key (`prog_key`, read as a big-endian number) by binary search; the entry's `stage` says which NVN stage it is. A shader is made once per key: the base module decompressed and `vkCreateShaderModule`, its c1 bytes copied into a uniform buffer kept for the process; variant modules are made when a pipeline first asks for them. Refused once per key with a `[RED]` line, their draws skipped: NV-only capabilities (none since the answers), interlock, a geometry or tessellation stage the device lacks, an `UNKNOWN` binding. NVN binds programs per stage, so each stage takes its shader from the program last bound to it (`nvn_mtl.m`'s `bind_stages`).
3. **Layouts.** Set 0: the union of the stages' set-0 records, cached by content: a push-descriptor layout when its descriptors fit `maxPushDescriptors`, else a set per draw from pools of the submission's slot. Set 1: the pool layout of `vka_tex.c`, bound only for shaders with pool records; the pool tables leave 5 × 64 descriptors of each kind under the device's update-after-bind limits for set 0.
4. **Pipelines** are keyed on the shaders, the layout, the pixel shader's [variant](#variants) and what EDS3 would have made dynamic: attachment formats and sample count, per-attachment blend state and write mask, logic operation, polygon mode, depth clamp, alpha to coverage, topology class, the depth convention (`SpecId 0` on the last pre-raster `F_GL_DEPTH` stage unless the game set `NEAR_IS_ZERO`), the alpha function (`SpecId 1` on an `F_ALPHA_TEST` pixel shader, 0 when the colour state's function is `ALWAYS`); and the vertex input when the device lacks `VK_EXT_vertex_input_dynamic_state`. Variant: `MOD_UINT` when every target the shader writes is a `UINT` attachment, `MOD_UINT_MIXED` when the `UINT` ones are exactly `uint_mask`, `MOD_DUAL` when target 0 blends with a `SRC1` factor and the device has `dualSrcBlend`; else the base. Outputs the shader does not write, and outputs whose class (after the variant) is not the attachment's (a `SINT` target), get write mask 0; without `MOD_DUAL` a `SRC1` factor reads zero. Dynamic: one viewport and one scissor, cull mode, front face, topology, depth and stencil tests and masks, depth bias, rasterizer discard, primitive restart, blend constants, vertex input. One `VkPipelineCache`, read from and written to `$DM_TEMP/vk_pipelines.bin` (`DM_VK_PCACHE` overrides).
5. **Per draw or dispatch** `vka_walk` turns each record into its source, as `encode_args` does on Metal: uniform slot → the bound range (in place when `minUniformBufferOffsetAlignment` allows, else a copy of the CPU's bytes); `SBUF` / `SBUF_UBO` / `UBO_PTR` → the address rounded down to `ssbo_align`, the range grown by the difference (a library without `ssbo_align` binds the exact address and refuses a draw off the device's alignment); combined slot → the view of the texture ID in the record's `dim` shape and the sampler of its sampler half; handles and addresses in uniform buffers read from guest memory with the bound pools' bases; `DRVCB` → a fresh buffer filled by `vka_drv_fill` (c0 storage tables, point size 2047, base instance, the sample table, dispatch size and compute uniform table; c2 handle tables; the push block); `SUPPORT` → zeros with `render_scale` 1.0, and in the fragment stage of an alpha-tested draw word 0 = the reference's float bits; `GMEM_MAP` / `GMEM_LOG` → the chunks' address table and a cleared log. An indirect dispatch copies its GPU-written counts into c0 first.
6. **Unbound slots** read a null descriptor (`VK_EXT_robustness2` `nullDescriptor`), else a zero buffer (storage: a sink) or a 1x1 zero image of the record's shape.

Not done yet, each logged once when met: `SINT` attachments, float vertex formats into integer inputs (bound as the same layout in the input's class), transform feedback, texel buffers, DrawTexture, tessellation, quads and line loops through indirect draws, viewport swizzles other than a y flip, the base instance of indirect draws in c0, the gmem write log's pages.

Draws and dispatches run only with placed guest memory (or `DM_VK_DRAW=1`); on an emulator without it they are skipped (`DM_VK_DRAW=0` turns them off anywhere). Events, counter reports and fences are written by the completion thread whatever happens to the draws. `DM_VK_SHLIB_CHECK=1` (a game run) makes every module and variant of the library and every compute pipeline right after it loads (`[vk] shader library check: …`); the graphics selftest does the same for the library `DM_VK_SHLIB` names.

Device features the DKB library asks for: `geometryShader` (7 modules), `shaderStorageImageWriteWithoutFormat` (161) and `ReadWithoutFormat` (30), `shaderDrawParameters` (every vertex module), subgroup ballot / shuffle / vote (344), `bufferDeviceAddress` with `shaderInt64` (2 modules), and, for `MOD_DUAL` modules, `dualSrcBlend`. No NVIDIA-only capability is left.

## Open problems

1. **Subgroup size** (closed): the job answer `subgroup_size: 64` ([Translator answers](#translator-answers)). The `F_SUBGROUP` modules split ballots and lane masks into 32-lane halves and shuffle within 32-lane segments; checked in the SPIR-V (two ballots per vote / ballot, `SubgroupLtMask` component 1, `laneId & 32`). Not yet run on Adreno: a compute workgroup whose 32-lane warps the game relies on (warp IDs, shared-memory layouts by warp) is still a question for the phone.
2. **Storage buffer alignment** (closed): the job answer `ssbo_align: 64`; every `SBUF` / `SBUF_UBO` / `UBO_PTR` access computes its offset from the base rounded down to 64 (`OpBitwiseAnd … -64` in the modules), so the replay binds at `addr & ~63`. If a device's `minStorageBufferOffsetAlignment` is above 64 (Vulkan allows 256), the library must be built with that value.
3. **NV-only geometry** (closed): the job answer `gs_passthrough: false` and the viewport mask kept in a `Private` variable: the four passthrough geometry shaders (DKB's terrain culling one, `5d537f7630ec3671`, among them) have no NVIDIA capability or extension left. What remains: a primitive whose mask names viewports other than 0 is drawn in the pipeline's viewport (`F_VIEWPORT_CULL`).
4. **Fragment shader interlock** is declared but used by no DKB shader (the capability is dropped); a game that uses it needs `VK_EXT_fragment_shader_interlock`, not in the probe.
5. **Variants:** built: integer colour outputs (`MOD_UINT`, `MOD_UINT_MIXED`), dual-source blending (`MOD_DUAL`, for `dual_want.tsv`; DKB has none, and a DKB pipeline that blends with `SRC1` needs the Mac host's `DM_NVN_DUAL_WANT` table first), the alpha test (a specialization constant, [Variants](#variants)). Not built: `SINT` attachments, integer vertex formats fed to float inputs (`dmsh_vin`), transform feedback (`vs_tf`, or `Xfb` decorations from `tf_layout`), the base instance of indirect draws (`vs_base_instance`, through `BaseInstance`).
6. **Size.** The translator runs in debug mode (`XLATE_DEBUG` default 1, the chain's option): its SPIR-V is full of temporaries. `spirv-opt -O` takes a module to about 40 % (measured on three), zstd to about 20 %; the library is stored with zstd. Optimizing too would change the code the phone runs against the Mac's, so it is left for when the replay runs.
7. **Pool view types:** see the aliasing note above; and a combined or storage image traced to no slot is not in the ABI (kind `UNKNOWN`; none on DKB).
8. **Tessellation:** the build passes hull and domain shaders through like the others (stage ranges 1 and 2), but no game here has one and their `c0` storage tables were never measured.
9. **Not run on the phone.** Everything above is checked by `spirv-val` only; no module has been through Adreno's compiler.
